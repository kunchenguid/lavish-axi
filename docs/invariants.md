# Implementation invariants

This file owns Hilight's architecture internals, security rationale, and easy-to-reintroduce failure modes.
[AGENTS.md](../AGENTS.md) keeps only the every-session rules and points here.
[README.md](../README.md) owns the user-facing contract. Runtime guidance strings in `src/cli.js`, `src/design-reference.js`, and `src/playbooks.js` own what agents are told while using Hilight.
[VISION.md](../VISION.md) owns the acceptance policy.

When a change touches an invariant below, update this file. When it touches a user-facing contract, update the README instead.

## Architecture

Hilight is a CLI + local HTTP server that opens agent-generated HTML artifacts in a browser, lets the user annotate elements and selected text ranges or edit Mermaid diagrams as whiteboards, and ships that feedback back to the agent over a long-polling API.

### Process model

Tailscale detection (`src/tailscale.js`) resolves each command candidate to an executable regular file before calling `execFile`: absolute paths are checked directly and bare names are resolved through `PATH`. Unresolved candidates are skipped without a launch attempt, because even an attempted launch of a missing binary can trigger managed-device software restrictions. Resolution and probe errors remain non-fatal, and all candidates share one probe timeout budget. `test/tailscale.test.js` covers skipping missing, directory, and non-executable candidates while retaining probes of installed executables.

The CLI (`bin/hilight.js` -> `src/cli.js`) spawns `hilight server` as a **detached** background process (`src/cli.js:startServer`) and waits for `/health`, which returns `{ ok, app, version }`.
Later CLI invocations reuse the running server when its health version is equal to or newer than the current CLI version, and replace it when the version is older, missing before the handshake, or unparseable, or when the local-build force applies. Releases up to and including 0.1.86 still replace a server of a different version. Stale servers are asked to `POST /shutdown`, and a pre-handshake server may be SIGTERM'd only through the PID `lsof` finds listening at its exact address and port whose command is Hilight (`killLavishListener`); other processes can share the port at other addresses, so nothing is ever signalled by port alone, and an unidentifiable listener is reported instead.
Host, port, listener, and link-host resolution lives in `src/paths.js`; the default path detects Tailscale and gives `serve()` separate concrete loopback and Tailscale listeners, and an explicit `HILIGHT_HOST` disables that automatic path but still adds loopback beside the pinned address. Loopback is always requested because it is the one address every CLI probes regardless of its own `HILIGHT_HOST`: agents on one machine run with different settings, and a server pinned to the tailnet address alone was invisible to a client with no host, which then spawned a second daemon on the same port and the same `state.json`. Wildcard requests are reduced to loopback before listening, and aliases are DNS-resolved and rejected if any result is an all-interfaces address. A name that does not resolve right now is kept as the name (`keepUnresolved`) on both sides - the server binds and retries it like any failed address and reports it in `network_warning`, and the CLI still requires it - so a DNS failure never silently drops an explicit `HILIGHT_HOST`. `listenOnce` resolves a name through the same lookup and all-interfaces refusal as startup, and `requested_hosts` reports configured names beside the addresses they resolved to, so a name whose DNS recovers is compared by address and never looks missing to a CLI that resolves it. Loopback binds FIRST and is the port's ownership lock: if it is in use by a Hilight server (probed over `/health`, bounded), startup throws before taking any other address, so two servers started concurrently cannot split one port between them. Every concrete address gets the same bounded bind retry, and the "did anything bind yet" check runs AFTER those retries and after the loopback floor below - ordering it first made both unreachable whenever the first (or only) host failed. When nothing binds and loopback was not among the requested hosts (explicit `hosts` only), `serve()` binds loopback as a floor. At least one listener must be an address the CLI control channel probes (the primary requested host or loopback), otherwise every listener already bound is closed and startup throws. A requested address that still fails is NOT given up on and never marks the server stale: it stays in `pendingBinds`, is retried in the background for the life of the process (`BIND_RECOVERY_DELAYS_MS`, last delay repeating) and immediately on `/health?reconcile_network=1`, and `applyNetworkState` recomputes the link host, Host allowlist, and phone readiness whenever a listener comes up. Restarting could not free a port another process holds and would drop every live review connection. Every surface that reports network health derives its text from `pendingBinds` (`currentNetworkWarning`), so the warning appears and clears with the bind state and is always logged, not only under `--verbose`. Every mutable the request handlers touch (`idleTimer`, `attachmentSweepTimer`, `bindRecoveryTimer`) is declared before the first listener binds: a reconnecting chrome can attach a live-event socket while later addresses are still retrying, and declaring them after the bind loop was a TDZ `ReferenceError` that crashed restarted servers. CLI discovery (`findRunningServer` in `src/cli.js`) probes the configured host, loopback, and every local interface address in parallel, each bounded, and a response whose `app` is `hilight` wins over a foreign `/health`. Both health probes (`fetchHealth` in the CLI, `probeLavishHealth` in the server) use `node:http` with the socket destroyed on every exit path, never `fetch`: an aborted fetch leaves its TCP connect running, and a Tailscale IPv6 address that drops connections to itself kept every CLI invocation alive ~10s after printing; a connection nobody reads likewise holds the other side's `close()` open. `/health` reports `state_id` (hash of the state file path), `state_dir`, bound `hosts`, and `requested_hosts`. Installation identity is `isOwnedServer`: a matching `state_id`, or - for a 0.1.77-or-older server that reports none - an answer at the CLI's configured host or loopback, where replacing it is the upgrade path; one reached only through the interface sweep without a `state_id` is never adopted or stopped, and another installation's server at a control address is a `SERVER_ERROR` naming its state directory, never used, replaced, or stopped. The CLI adopts the first owned server, retires any other owned server on the port over its own `/shutdown` (never by process name or port-wide signal), and replaces the kept server first when it does not request every address a retired duplicate served (`hostsToServe`), so existing review links survive. It also replaces a server whose `requested_hosts` lack the CLI's explicit host, rechecked once in the startup wait loop when another daemon wins the port, so agents with different hosts converge on one daemon instead of trading it; a server still missing that host after the one retry (including after a network restart) is a `SERVER_ERROR` naming the address, never a successful open. Every replacement - missing host, upgrade, or changed network - passes everything the replaced servers requested to the new one (`inheritedListenHosts` -> `--also-listen`), so one agent's restart never drops another agent's address and its review links; only an IP that is no longer on a local interface (`localInterfaceAddresses`) is dropped, so a vanished Tailscale address is not retried forever while a still-live one survives a MagicDNS change even when the replacing agent's explicit host disables Tailscale detection. A Tailscale identity change (address, MagicDNS, up/down) still reports `network_stale` and is replaced by `ensureServer`, at most once per invocation including the replacement performed before the startup wait loop; a version-driven replacement does not consume that network guard. A version-driven replacement happens only when the running server is OLDER than the CLI (`isServerOlderThanCli`, numeric on major.minor.patch): a newer server is adopted, because replacing it in either direction made two installed versions restart each other's server and interrupt every live poll. Releases up to and including 0.1.86 still replace a server of a different version, so this stops only when both installed versions contain this fix. The same test gates the SIGTERM fallback (`shouldKillProcessOnPort`) and the `upgrade` reason. A missing or unparseable version still counts as older, and the local-build force still replaces a server of any version.
Two global middlewares run before every route, in this order: a Host-header allowlist, then a mutating-route Origin/Referer guard. The Host allowlist (`buildAllowedHostnames`/`isAllowedRequestHost`) rejects any request whose `Host` is missing or not one this server answers to - the DNS-rebinding defense, since `isSameOriginRequest` alone does not stop rebinding (a rebound page sends its hostile domain in _both_ `Origin` and `Host`, so they still match). The allowlist is loopback names + every concrete listener + the active link host + explicit `HILIGHT_ALLOWED_HOSTS` extras (`src/paths.js:extraAllowedHosts`), minus wildcard binds; the Tailscale address and MagicDNS name enter it only while the Tailscale listener is usable. A lone `*` (`allowsAllHosts`) disables the guard for operators fronting it with their own auth. When a reverse proxy sits in front, `X-Forwarded-Host`'s outermost value is validated as a complete authority against the same allowlist (an AND check, so a spoofed or malformed forwarded host only narrows access, never bypasses `Host`); the `*` opt-out skips hostname membership but still rejects malformed authorities. README's Allowed hosts bullet owns the user-facing contract. So a specific-interface bind stays rebinding-protected while its own hostname works, rather than the guard switching off outside loopback. The origin guard then 403s non-GET/HEAD/OPTIONS requests whose Origin (else Referer) is present and does not match this server's origin, using the same construction as `isSameOriginRequest` (including forwarded host/proto). Header-less CLI control-channel requests have no Origin and must keep working; the Host allowlist remains their gate. Per-route `isSameOriginRequest` checks stay in place and still reject header-less callers.
README's Network binding bullet owns the user-facing env vars and the non-loopback security warning.
Live-event WebSockets carry an application-level ping/pong (`liveEventHeartbeatMs`) and an unanswered ping terminates the socket, because a slept laptop or a dropped tailnet path leaves a half-open connection that never emits `close` - which otherwise keeps a departed reviewer counted, suppressing idle shutdown and reporting presence wrongly. Every `shutdown()` records a log-only `cause` (never widened into the user-facing `reason`, which would let an internal cause render as a banner line that claims something untrue), and default log lines are UTC-timestamped by `formatServerLogLine` because `server.log` is append-only across restarts. Detached server stdout/stderr are timestamped inside the server process at real line starts so crash diagnostics in `server.log` stay dated after the parent CLI has already exited; an injected `log` still formats its own lines. The detached spawn uses `bin/hilight-server.js` (published as `dist/server.mjs`), which installs that writer before dynamically importing the CLI, so a module-load failure is dated too. Each HTTP listener keeps its `error` handler after `listening`, so a post-listen error is logged instead of becoming a fatal unhandled `EventEmitter` error. The detached entrypoint also logs `uncaughtException` through timestamped stderr and exits 1 explicitly; installing that listener without an explicit exit would suppress Node's default termination and leave a potentially corrupted server alive. Ordinary user-facing commands still start through `bin/hilight.js` / `dist/cli.mjs`. Server self-shutdown keys off tracked live connections (browser WebSockets and agent polls), not session status, so the next `hilight <file>` re-spawns a fresh server and adopts the session from `state.json` when it is still resumable; README's Server cleanup bullet owns the user-facing idle-timeout rules. The retained legacy SSE route is only a one-response migration handoff, not a tracked persistent connection.
State lives at `~/.hilight/state.json` (`HILIGHT_STATE_DIR`), shared across all projects and keyed by a sha256 prefix of the canonicalized file path - the canonical HTML path _is_ the identity, so the CLI never needs opaque session IDs (`src/session-store.js:sessionKey`).
That makes the session key **derived, not secret**: anyone who learns the artifact path (or sees a session URL) knows it, so no route may treat key possession as authorization.

### Request flow

1. `hilight <file.html>` (`openCommand`) -> POST `/api/sessions` -> `SessionStore.upsertSession` -> the CLI opens the returned session URL in the browser.
   `--no-gate` sends `noGate`, returns a one-open URL with `?no-gate=1`, and leaves the stored canonical session URL unchanged.
   Sessions record who ended them: `ended_by: "user"` for browser-initiated ends (including the More menu's **Send all and end session**, which posts final prompts and the `endSession` flag to `/api/:key/prompts` atomically) and `ended_by: "agent"` for `hilight end <file>`.
   Idle self-shutdown never calls `endSession` - it only stops the server process, leaving session status untouched in `state.json`, so there is no third `ended_by` case to track.
   `/api/sessions` refuses a path that is not a regular `.html` / `.htm` file after `realpath` (`src/artifact-path.js:resolveAllowedArtifactFile`), matching the CLI, so a caller cannot register `/etc/passwd` (or an HTML symlink to it) and adopt that directory as a serving tree.
   `/api/sessions` refuses to revive a user-ended session unless the request body sets `reopen: true` (the CLI's `--reopen`), returning `{ status: "user-ended" }` without upserting; agent-initiated ends keep reviving on a plain open.
2. `GET /session/:key` serves a chrome page (`createChromeHtml`) whose sandboxed iframe points at `/artifact/:key/index.html`; the chrome client bootstraps from the `lavish-session` JSON script in the page.
   `extractArtifactHead` (`src/server.js`) adopts the artifact's own `<title>` and `<link rel="icon">` for the chrome tab, but only `data:`, `http(s):`, and protocol-relative icon hrefs - artifact-relative hrefs would not resolve against the chrome page - with fallback to the Hilight defaults.
3. The artifact route runs `injectLavishSdk` (`src/html-transform.js`) to append one `<script src="/sdk.js?key=...">` at the end of `<body>`. Nothing else is injected - artifacts stay byte-identical apart from that tag so they remain portable when opened directly without the server.
4. Sibling assets resolve under `/artifact/:key/<path>`, sandboxed to that session's **artifact tree** - the directory of the canonical HTML file - both lexically and by **real-path/symlink resolution**. `resolveArtifactAsset` (shared with `/whiteboard-assets/*`) rejects `..` escapes and, in parity with export's `guardedRead`, a path whose symlink-followed real path leaves the tree, so a symlink placed beside the artifact can't make the route serve an outside file; a nonexistent path (`ENOENT`/`ENOTDIR`) falls back to the lexical check for the caller's 404, and every other realpath failure fails closed. It returns the **resolved** path, so `sendFile` re-opening it cannot be redirected by a link swapped in after the check. `sendFile` still uses `dotfiles: "allow"` so a tree that _lives under_ a dot-directory (`.lavish/artifact.html`) is not 403ed by the absolute path. A stored session whose file is not HTML is refused on `/artifact`, `/session/:key`, export, share, and mermaid-sources before those routes read `session.file`. The packaged Tailwind/DaisyUI assets are still served from `/design/:asset` so older artifacts keep working, but new artifacts are no longer auto-wired to those routes.
5. The injected SDK runs the render-time layout audit and posts each pass - findings plus its own `complete` flag and viewport width - to the chrome. A completed client-side pass releases the visual gate immediately, then the chrome reports it fire-and-forget to `/api/:key/layout-diagnostics`; a failed report must never hold the artifact behind a network round-trip. If a pass loses an artifact-load-token race, the chrome requests a fresh pass instead of silently consuming the cycle.
   Detection is **passive**: that route updates the warning inbox and emits a live `layout-warnings` event, and it deliberately never emits `feedback`, so a diagnostic pass can never make `hilight poll` return or wake an agent. The gate reveals on the first completed pass whatever it found (detection and user-facing behavior: README's Layout issues inbox, Layout issue lifecycle, and Open-time layout gate bullets).
   Cosmetic, intentional, transient, tiny, warning-severity, and uncertain observations fail open and never enter the inbox.
   The narrow **fatal** path is separate and still immediate: `/api/:key/artifact-failures` records only `artifact-unavailable` (the chrome's probe of the artifact route failed) or `artifact-asset-unavailable` (the SDK saw a same-origin subresource `error`), marks the session `feedback`, and `takeFeedback` returns them as `artifact_failures`. Ordinary layout findings must never be relabelled fatal to regain auto-repair.
6. User actions in the iframe `postMessage` to the chrome. Queued prompts live in tab `sessionStorage`; unsent prompts sharing the SDK-internal `_lavishQueueKey` replace each other, and that field is stripped before POSTing collected prompts to `/api/:key/prompts`.
   The chrome assigns each queued prompt a unique `prompt_id` at queue time (never trusting an iframe-supplied value), carries it through `queuePrompts` onto the persisted transcript entry, and removes a queued note solely when that transcript acknowledges the same identity - never by displayed content or only by a successful POST response - so a reload after a lost response recognizes an already-accepted note instead of re-sending it. `queuePrompts` filters acknowledged identities before attachment resolution and layout-warning planning, and reports whether it accepted fresh feedback so an idempotent retry neither conflicts with newer warning state nor wakes an unrelated poll. Visible `session.chat` is bounded to `MAX_CHAT_STORED_BYTES` (5,242,880) of stored JSON on every shared state load and transcript append; legacy overflow is persisted before the session is served. Evicted user entries leave their `prompt_id` on `session.chat_ack_ids`, and both the store's ack filter and the chrome's settlement (`initialChatAckIds` / live `ack_ids`) consult that compact list so eviction cannot reopen duplicate send. `chat_revision` lets the chrome accept an authoritative bounded replacement even when no retained entry overlaps its current view, while rejecting stale syncs.
   Editing a queued note happens only in the chrome: the edit rewrites `prompt` on the same queued object, so its `prompt_id`, anchor, and send bookkeeping (which tracks notes by object identity) are unchanged, and a note that is already Sending cannot be opened. The iframe learns only the selectors of element-anchored queued notes (`lavish:queuedAnchors`), never their text, and asks the chrome to open one with `lavish:editQueuedAnchor`. The artifact is agent-authored, so a design where the SDK held or rewrote note text would let any artifact script read or silently rewrite the reviewer's instructions; the forgeable message can only open one of the user's own notes for editing.
   The conversation transcript is server-owned display state. Every accepted prompt with text or images enters `session.chat` through `chatEntryForPrompt` (`src/chat-messages.js`) as a bounded `{ role: "user", kind, text, anchor, attachments, at, prompt_id }` entry - not only composer messages - and `/api/:key/prompts` answers with the serialized transcript and emits `chat-sync` at accept time, so the sending chrome settles its queued bubbles in place and every other tab shows the sent notes before any poll takes the batch. Rendering is computed server-side by `serializeChat`/`renderChatMarkdown` in that module because `chrome-client.js` is served as a raw file and cannot import modules (the same reason layout-warning display strings and share passwords are): agent entries ship with their rendered `html` and are the only entries the chrome ever sets as html; user entries ship as text with their anchor and are always escaped. There is no queued log: `visibleThreads` and `pageThreadMessages` render the tab's unsent prompts as **Not sent** messages inside the thread they belong to (a new anchored note as its own card, an untargeted one in the page thread), and `promptAnchor` in the chrome deliberately duplicates the server's anchor rule for prompts that have not reached the server yet; `test/chrome-client-queue.test.js` pins the two against the same fixtures so a message never changes its anchor when it settles. A note's Sending state is derived from the existing send bookkeeping (`snapshotRequests`, `pendingSubmissions`, the active submission, the terminal reservation), never tracked separately, so no failure path can strand a note with its Edit and Delete controls hidden.
   `/api/:key/prompts` is **same-origin guarded** like `/share` and the whiteboard write routes: whatever lands there reaches the agent as the reviewer's own instructions, and the key alone must never buy that. Only this server's own chrome may queue prompts, so any test or tool that posts there has to send a matching `Origin`; behind a reverse proxy, the expected origin is built from the outermost `X-Forwarded-Host`'s validated hostname and port plus the outermost `X-Forwarded-Proto`, only after the forwarded authority passes the same allowlist boundary as `Host` (or strict authority validation under the `*` opt-out).
   The route rejects every new batch for an already-ended session, including a redundant send-and-end batch, because no later poll will deliver it. `SessionStore.queuePrompts` exempts only its internal `restore` replay of a batch that was accepted before a poll disconnected.
   The chrome page (`/session/:key`) also answers `X-Frame-Options: DENY` and `frame-ancestors 'none'`, denying an attacker page both a window handle to the chrome and a clickjacking surface over Send. The header is scoped to that route on purpose - `/artifact/*` is framed by the chrome, and `/whiteboard-frame` is framed by the artifact document (see the whiteboard section).
   Text selection prompts use `tag: "text"` with a `target` of `type: "text-range"` (selected text, `commonAncestorSelector`, start/end boundary anchors).
   Mermaid diagram-node prompts for rendered SVGs outside `.mermaid` containers use `tag: "mermaid-node"` with a `target` carrying `diagramId`, `nodeId`, the rendered `label`, and a `selector`, so the annotation anchors to node identity and survives a re-render that reshuffles the SVG.
   Page-comment, reply-box and annotation-card keyboard conventions, button layout, and the comments margin are user-facing behavior owned by README's Feedback controls and Keyboard shortcuts bullets.
7. `hilight poll <file.html>` (`pollCommand`) hits `GET /api/poll`, or `POST /api/poll` when it atomically publishes an `--agent-reply` before waiting.
   Poll ownership is exclusive per session and lives only in the server's `activePolls` map. A second poll receives typed `LISTENER_ACTIVE` with the holder label and age; `--takeover` installs its holder before releasing the old poll with typed `LISTENER_REPLACED`, so cleanup cannot erase the successor. The in-process map also supplies the listener labels exposed by `/health` for session listings. Claims serialize through `pollOwnershipLock`, including the reply write, so a rejected poll cannot publish or duplicate its reply. Poll control GETs and POSTs reject a present foreign Origin or Referer while preserving header-less CLI access.
   Queued prompts or fatal artifact failures - including prompts queued before an ended session - are returned immediately and mark the session as observed by an agent; otherwise the poll marks the session actively listening and long-polls on an `EventEmitter` until a `feedback` or `ended` event fires.
   A waiting no-timeout response carries `Lavish-Poll-State: listening`; immediate feedback does not. The CLI uses that response signal for the opt-in Herdr chime, so it never announces a review-ready wait when feedback was already queued, and notification failure must never affect the poll.
   A user-queued layout-issue batch arrives here as an ordinary `tag: "layout-warnings"` prompt with a `type: "layout-warnings"` target - indistinguishable from other feedback at the CLI boundary, which is what lets a nonblocking relay consume it without special handling. `layout_warnings` is no longer a poll field.
   A `status: "ended"` response carries `ended_by`; the final `status: "feedback"` batch delivered right before a session ends carries the same signal via `session_ended: true` plus `ended_by`, so that last `next_step` also skips the reopen instruction.
   Default no-timeout polls stream whitespace heartbeat bytes before the final JSON response and always write the one-shot wait banner to stderr once the response headers arrive (full on a session's first delivery, one line after that, keyed off the `Hilight-Delivered` header the server sets from `delivery_seq` before the take) - it is the "not hung" signal an agent needs while stdout stays empty - but write the recurring per-minute wait ticks only when stderr is an interactive terminal (`shouldNarratePollWaitTicks`), so agent harnesses with piped, non-TTY stdio get no unbounded tick noise in their merged capture; stdout is always reserved for the final JSON/TOON response, and `--timeout-ms` is a non-streaming test/debug escape hatch.
   Losing the last review WebSocket while a poll is active starts a per-session reconnect grace timer; a reconnect cancels it, while expiry releases the poll with non-terminal `browser_disconnected` and leaves the stored session open. Poll cleanup must cancel that timer so a timeout, feedback, or explicit end cannot leave a stale disconnect event for a later poll. A disabled grace (`resolveBrowserDisconnectGraceMs` returns `null`) must schedule no timer at all, never a `null`/`0` delay, which `setTimeout` would fire almost at once.
   Key order in `createPollOutput`'s feedback object is a contract, not incidental: `prompts`, `artifact_failures`, `changes`, then `next_step` all come before the unbounded `dom_snapshot`, which appears only with `--full` (otherwise `changes.page_snapshot` gives its size and points at `catch-up --full`), so an agent that truncates or filters the response still reaches the user's own words and the instruction that continues the review loop (`test/cli-output.test.js` guards the emitted order). Never move `next_step` after the snapshot: it is the only field carrying the reply-and-poll-again directive, the attachment paths, and the session-ended "stop polling" rule. Poll delivery consumes the response - the feedback is gone from the store once returned - which is why the guidance strings say feedback remains queued only _until delivery_ rather than that it is never lost.
   Delivery is changes-only and never guesses whether the agent remembers the review. A prompt row is `thread_id` (`page` for the page thread), `on` (the card title or anchor from `threadAnchorLine`, computed server-side from `session.threads`), `text`, and `files` only when there are local files to read; earlier messages in a thread are never resent. `changes.code_cards` compares each code card's status with `agent_code_status`, which `exchangeAgentCodeStatus` swaps on every delivery: the first delivery counts only drifted cards (since pinned), later ones any status move (since your last turn). Every `next_step` ends with the `hilight catch-up <file>` line instead; the full `next_step` goes out on the first delivery only (same header), later ones get one line, and a held reply always keeps its full text; `GET /api/:key/review` backs that command, never writes, and refuses a foreign Origin like the other poll control routes.
   A reply that arrives while prompts are pending is held, not posted: `holdReplyForPending` takes the new prompts and answers `status: "held"` with them, through the same `finishFeedbackDelivery` (or the closed-request restore) as an ordinary delivery, so the agent answers them in the same turn and the final reply covers every batch. Validate the reply's `## <thread_id>` sections first, so a bad reply is refused before anything is taken.
   If SIGINT or SIGTERM interrupts a no-timeout poll, the CLI writes re-run guidance to stderr and exits with the conventional signal code; queued feedback persists, so re-running the same poll is safe.
   That durability has to survive the take itself: `takeFeedback` clears the batch before any response is written, so a poll whose client disconnected - during the immediate take OR during the event-driven long-poll `respond()` - puts the prompts, `dom_snapshot`, and `artifact_failures` back through `queuePrompts`'s `restore` mode and leaves delivery unmarked, because nothing was delivered. `restore` replays an already-accepted batch verbatim - it re-plans no layout warnings and re-appends no chat messages - while still re-deriving attachments through the same resolver.
   Everything else about restore exists because the take window is concurrent, and each rule is load-bearing. Restored prompts are PREPENDED, so a `/prompts` that landed in the window keeps its later position and the user's chronological order survives. A newer `dom_snapshot` and newer `artifact_failures` WIN - the restore only fills what the window did not already replace, and the failure merge goes through the same `mergeArtifactFailures` dedupe and `MAX_ARTIFACT_FAILURES` bound as a fresh report, so a failure re-reported inside the window is not handed to the agent twice - including the end the bound trims, because the restore REPLACES that list: keeping its own never-delivered entries over the newer ones would delete failures nothing else holds, recorded in the window and never delivered either. At the bound the restore's own overflow is dropped and reported through the incomplete-restore log. A successful restore must re-emit `feedback`: a second poll can take `waiting` between the destructive take and the restore, and without that wake it long-polls forever over feedback already sitting in `state.json`. And a restore is exempt from the request-wide `MAX_REQUEST_ATTACHMENT_REFS` bound (never from the per-prompt cap or the resolver), because that bound sizes ONE untrusted POST while a delivery accumulates across an unbounded number of them - measuring a restore against it rejects the whole batch and causes exactly the loss restore exists to prevent.
8. The `/events/:key` live-event WebSocket emits server-derived `agent-presence` data. Its state is `waiting` before any poll has attached, `listening` while one is active, and `working` after a poll has delivered feedback and released. Its mode distinguishes `agent-listener`, an owner-labelled `external-listener`, `agent-busy`, and `waiting-on-captain`; the chrome uses external mode to avoid presenting a supervisor-owned listener as an idle captain turn. While the session is open, the chrome keeps feedback actions available because the server queues them for the next poll. An agent reply concludes the working state and returns presence to `waiting`, and a batch delivered with `session_ended` releases it immediately because no later poll or reply can.
   A 200 from `/api/:key/prompts` acknowledges the queue write, not a completed round, so the chrome never promotes itself to `working` on send and renders only the state the stream reports. A successful ownership claim retires the previous round's delivery marker; releasing a poll never does. Presence reconciliation compares state plus mode so a takeover between bare and owner-labelled listeners is visible even when both states remain `listening`.
   Per-note delivery receipts ([docs/delivery-acks.md](delivery-acks.md)) are the same facts stamped on the user's chat entry: `takeFeedback` writes `delivered_at`/`delivered_seq` (Seen), the artifact `reload` event after a delivery writes `working_at` through `markWorking` (Working), and `addAgentReply` writes `done_at` (shown as Replied), each only where the previous stamp exists and the next does not. Seen is stamped **by position under the store lock**, not by id: `agentFacingPrompt` strips `prompt_id` from stored prompts at queue time, and because a take drains every pending prompt while `queuePrompts` shares the lock, the user entries with no stamp are exactly the batch being delivered. `session.delivery_seq` numbers takes so a closed-poll restore (`restoreClosedFeedback` passes `delivery_seq` back) removes **only that take's** stamps - deleted, never nulled, because the restore tests assert the entry is byte-identical to its pre-take shape - while a note queued in the window stays unstamped and is delivered by the next take. A refused restore (an attachment no longer resolves) re-queues nothing and still removes that take's stamps and publishes `chat-sync`: a note that reached no agent must not read Seen. Working and Done never cross a reopen: `#upsertSessionLocked` records the last take of an ended session as `closed_delivery_seq`, and `stampWorking`/`stampDone` skip entries delivered at or before it, so a note `hilight end` left at Seen is not marked by a later round's edit or reply. Every stamp change bumps `chat_revision`, which is what makes `syncChat` accept the replacement; `chat-sync` for a delivery is emitted from `finishFeedbackDelivery` (the success path) and again after a restore, never from the destructive take, so no tab is told Seen for a batch about to be put back. `delivery_seq` is stripped from the poll response by `agentFacingFeedback`; agents never see it. A session with no `delivery_seq` key at all predates receipts: `readState` marks its user entries `receipt: "none"` and persists that before any take runs, because the positional rule would otherwise read every one of them as the first post-upgrade batch; marked entries are skipped by every stamp helper and render no receipt row. The chrome derives each thread's one status word (`threadStatus`/`deliveryLabel`) from the latest message's entry on every render; presence lives only in the top bar's `#agentStatus` and never changes that word. Cards are rebuilt only when `threadSignature` changes, so an "Image expired" placeholder is not rebuilt into a retried image by an unrelated render.
   An `ended` live event makes every connected chrome read-only immediately. The channel registers before reading session state, then sends an `ended` snapshot when that state is already terminal; the bootstrapped `initialEnded` state covers pages loaded after the end, and `markSessionEnded()` is idempotent across redundant signals.
   Every poll exit path has to undo the presence it set: `/api/poll` subscribes to request and response closure before its first `await`, re-checks closure and replacement after destructive feedback takes, and reconciles a browser disconnect that occurred before event handlers were armed. This prevents abandoned or displaced polls from stranding ownership, presence, or consumed feedback.
   `--agent-reply` and `--agent-reply-file` publish a chat message through the same atomic poll claim before waiting, rendered in the browser's page comment thread via the live stream; README's CLI reference owns when to use each input. `hilight reply` posts that same message to `POST /api/:key/agent-reply` and exits 0 only after the route answers `sent`. The whole receipt request (connect, headers, body) shares one deadline, `AGENT_REPLY_RECEIPT_TIMEOUT_MS`, and a timeout exits non-zero. It must not claim a poll: a poll stays open until feedback arrives, so it cannot be the acceptance receipt.

### Margin comment threads

`src/comment-threads.js` owns thread recording and reply routing as pure functions; `SessionStore` persists `session.threads` beside, not inside, the bounded chat transcript, so eviction never loses a thread. An anchored note (anything with a selector except `message`, `whiteboard` and `layout-warnings`) opens a thread with a server-minted short id (`c1`, `c2`, ...) that poll prompts carry as `thread_id`. Settlement still uses the chrome-minted `prompt_id`, so a retried send records its thread message once, and a disconnected-poll `restore` never appends thread messages again. Threads are never deleted: resolving only hides them, and a reply from either side reopens them.

Agent replies are routed by `planThreadReply`: `## c<n>` or `## c<n> reveal=<revision-id>` on a line of its own (outside fenced code) starts a thread section; everything before the first one is the chat part. Every section is validated before any write, and an unknown id is a 400 `VALIDATION_ERROR` for both `reply` and `poll --agent-reply`. The poll route checks it before claiming the listener, so a typo never strands a half-claimed poll. Any reply still clears Working and stamps Done on every delivered note, unchanged. Only a non-empty chat part emits an `agent-reply` entry, which the chrome shows in the **Whole page** thread; threads travel in `chat-sync` with agent-only Markdown rendering. The page thread is derived purely in the chrome (`pageThreadMessages`: transcript entries with no `thread_id`, this tab's untargeted drafts, and retired drafts), so the CLI and server contract did not change when the conversation panel went away.

The chrome posts only thread ids, selectors and page-authored range targets into the artifact (`lavish:threadAnchors`), never comment text. The SDK paints highlights as overlays in its excluded shadow root without touching artifact DOM, re-checks that a text range still reads its saved text before highlighting it, and reports geometry (`lavish:threadGeometry`) through one coalesced animation frame, sending nothing when it is unchanged. In annotate mode a click on a commented element (that exact element, not its children) or inside commented text opens the thread instead of a second comment; explore mode keeps the page's own clicks. The margin places the open card at its anchor and pushes the others away without overlap. A thread reply's `revision_id` uses the existing registry and `revealNextRevisionMark`/`revealElement` path; a revision with no marked block disables Reveal rather than guessing. Resolve and reopen go through the same-origin-guarded `POST /api/:key/threads/:id` under the store lock; the chrome's Undo toast and the top bar's resolved drawer only call that route, so a resolved thread is hidden, never removed.

The margin is laid out in `positionThreads` from cached card heights (`threadHeights`), measuring only the open card per frame, so scrolling a page with many threads never forces a reflow of every card. Compact mode is decided from anchor spacing alone, which keeps it scroll-invariant: a card does not change size as it scrolls. The transform transition is enabled only through `.is-animating` while a card opens or closes; a standing transition makes cards lag the page while it scrolls. Enter in every comment box only saves a draft (`queueComposerMessage`, `sendThreadReply`, the SDK's `tryQueue`); the one **Send to agent** button is the only path that calls `sendQueued`, and the page box's half-typed text is kept in `sessionStorage` (`lavish-axi:page-draft:<key>`). New agent replies never scroll the margin.

### Passive layout-warning inbox

`src/layout-warnings.js` is the whole lifecycle, as pure functions over stored records, so it is unit-testable without a browser or a server; `SessionStore` and the routes only persist and serve what it returns.
Identity is `layoutWarningFingerprint` over rule + normalized target + viewport class - **magnitude is deliberately excluded**, so a finding that worsens updates one record instead of inflating the count.
Every observation is stamped with an **artifact revision**: `session.artifact_revision`, incremented by the server-owned `beginArtifactLoad` epoch before navigation. The artifact document route only verifies the current load and serves it. Every transition that needs "a newer successful artifact load" (resolved, recurring, dismissal expiry) keys off the revision.
The reviewer handoff is a server-issued single-reviewer capability. Begin requests return typed `superseded`, `no-handoff`, or `out-of-order` outcomes; the chrome may re-handshake once for `no-handoff`, but only an explicit takeover reload can replace a superseded reviewer.
The active load is **durable**, not process state: `beginArtifactLoad` writes the whole epoch - token, revision, pass fence, and the `request_id`/`request_sequence`/`handoff_token` a later begin is judged against - to `session.artifact_load`, and `SessionStore` restores it (and the handoff that owns it) the first time a process asks for it, because the `upgrade` restart replaces the server under reviewers who did not ask for it. Only a newer `beginArtifactLoad` retires a load - not a restart, and not reopening the session. A stored load the restore cannot read as a whole is treated as none, which degrades to one re-handshake and a fresh epoch. The restart tests in `test/session-store.test.js` and `test/server.test.js` pin all three.
`applyDiagnosticPass` is conservative by construction and each guard is load-bearing: a pass for one viewport class returns other classes untouched; an incomplete pass marks active warnings `unverified` instead of clearing them; absence at a revision the warning was already seen on is not resolution; and re-observing an identical finding on the same revision returns the record unchanged so repeat passes do not rewrite `state.json`.
`queued` is a request, not a fix - it stays in the active count and only `recurring` (a newer revision still found it) makes a warning selectable again.
A layout fix request that `planLayoutWarningPrompt` finds stale never blocks the unrelated prompts sent with it. If none of its conflicting warnings is still active (resolved or dismissed) and it queues nothing else, `queuePrompts` **retires** it: its `prompt_id` goes on `chat_ack_ids`, so the tab settles it through the ordinary acknowledgement path and a retried batch is the same answer. If a conflicting warning is still active, the request is **held**: it is neither delivered nor acknowledged, its id comes back as `held_prompt_ids`, and the chrome keeps it queued with copy telling the reviewer to remove or re-queue it. A batch with nothing sendable besides held requests, or any batch carrying `endSession` with a held request, keeps the whole-batch 409 `conflict`, because ending would strand the held note.
Display strings are computed server-side (`serializeLayoutWarnings`) because `src/chrome-client.js` is served as a raw file and cannot import modules; the chrome renders what it is given and never decides that a warning went away.
The chrome bootstraps the inbox from `initialLayoutWarnings` in the session JSON and re-syncs over the live-event channel, so the inbox survives a browser refresh or reconnect; only per-chrome drawer selection lives in `sessionStorage`, keyed per session so it cannot leak across artifacts.

### Live reload

While a session has a queued (not yet re-checked) layout-warning batch, the reload debounce widens to `BATCH_RELOAD_DEBOUNCE_MS` so an agent's related saves coalesce into one artifact refresh for that group.
`chokidar` watches the artifact file itself by default - watching the entire parent directory recursively saturated the event loop when artifacts lived inside large trees like `~`.
The opt-in attribute/meta (user-facing contract: README's Live reload bullet) switches the watcher to the artifact's directory, excluding `.git`, `node_modules`, `dist`, `build`, `.hilight`.
Any file change emits a `reload` live event and the chrome reloads the iframe; the SDK reports scroll position with `lavish:scroll` and the chrome replays it with `lavish:restoreScroll` after the iframe loads, because the sandbox prevents direct scroll reads.
The same channel preserves the rest of the in-iframe review context: `lavish:reviewState` carries an open annotation card's unsent text, the values of controls inside a `data-lavish-question` scope, and the `open` state of every `<details>` the reviewer toggled away from how the page wrote it, and `lavish:restoreReviewState` replays them after the load. A selected-text card's draft also carries its saved range target; the restore rebuilds the range only through `threadRange`, which re-checks that it still reads the same words, and otherwise reopens the words on the container selector rather than dropping them (a reload invalidates the live Range, and restoring it blindly could point the note at different text). Disclosures are keyed by id (else by selector), and only toggled ones are reported, so a save that deliberately changes a disclosure's default still wins for every disclosure the reviewer never touched. Restoration sets values directly and dispatches **no** synthetic `change`/`input` events, because the artifact's own handlers queue prompts and replaying them would silently re-queue answers. Application-owned form state outside `data-lavish-question` is deliberately left alone.
That reported state is also **persisted** per session (`lavish-axi:review-state:<key>` in `sessionStorage`, beside the queue's own key) and restored on boot, because it is the user's own writing and the chrome's in-memory copy dies with the document: an iframe live-reload replayed it, but a full page reload destroyed it, and a real user lost written notes that way. The SDK reports `card: null` when a card is queued or cancelled, which is what retires the stored draft, so a stale draft can never reappear over a later card. `closeCard` reports only when a card was actually open: a page declaring `data-lavish-annotate="off"` closes at boot, and a `card: null` sent then would overwrite the stored draft before the frame's `load` event replays it (`test/artifact-sdk-bundle.test.js`, "reports no review state at boot").
During version-driven shutdown, the server sends `chrome-reload` to the live-event clients of the ONE session named by `POST /shutdown`'s `reload_key` - the session `hilight <file>` is about to open - and `chrome-outdated` to every other connected chrome; a shutdown that names no key (`hilight stop`, idle self-shutdown) reloads nothing. `chrome-outdated` shows a dismissible notice under the top bar and never reloads by itself: a forced reload of a current page the user is reading or writing in is the behavior this replaced. The deliberate migration exception is an old EventSource client reconnecting to the retained legacy route: it receives one neutral `chrome-reload` event and the response ends immediately so the tab moves to WebSocket without occupying the browser's HTTP connection pool. `reloadChromeAfterServerRestart` still shows the banner instead of reloading whenever an unsent annotation draft exists. The same banner also carries the server-unreachable state: after `LIVE_EVENT_UNREACHABLE_FAILURES` consecutive live-socket reconnect failures the chrome raises it with the no-reason copy, because an endless silent retry is indistinguishable from a healthy quiet stream and the user learned nothing until they reloaded into a browser connection error. Only that path may retire a banner it raised - a `chrome-outdated` event means the server really was replaced, which a reconnect does not disprove - and a dismissal sticks until the stream actually recovers.
The banner's line is chosen by the shutdown's own `reason` (`SHUTDOWN_REASONS`: `upgrade` and `local-build` from `ensureServer`, chosen by `serverReplacementReason` from whichever branch of `shouldRestartServer` fired, and `stop` from `hilight stop`), and **every branch must be true where it is shown** - a deliberate stop told the user Hilight had been updated, which was false on both counts. An invalid reason on `/shutdown` is dropped and renders the line that claims neither; the legacy migration deliberately sends the unrecognized `server-restarted` reason because the replacement server cannot know why its predecessor stopped. Idle self-shutdown and `shutdownIfNoLiveSessions` need no branch: both only fire with `liveEventClients.size === 0`. Every recovery control this feature shows probes `/health` before navigating - the banner and both gate cards through `checkServerThenReload`, and the inline boot failsafe (`CHROME_BOOT_FAILSAFE_JS`) through its own copy of the same rule, because it runs where `chrome-client.js` does not exist. Each is raised in a state where nothing may be listening, and each is labelled for the check rather than the navigation. Every one of those probes is bounded by an abort timeout and every caller restores its own control on a path that runs whether the probe answers, fails, or times out - a port that accepts a connection and then says nothing would otherwise leave the user's only recovery button disabled, which is worse than the reload it guards. A new one that calls `location.reload()` directly reintroduces the browser error page this whole path exists to avoid; the `superseded` takeover card is the one exception, because its 409 proves the server answered.
The "Hilight is not running." card's copy is the one failure state only the user retires, so `setLayoutGateFailure` refuses to overwrite it with a non-sticky failure or clear that state. Sticky copy never makes the visual overlay sticky: every failure card retains the shared bounded timeout and independent **Show anyway** bypass.
A draft is retired only on a definite answer, and "definite" is deliberately expensive: the SDK re-queries the anchor after `REVIEW_DRAFT_ANCHOR_SETTLE_MS` before reporting `lavish:reviewDraftUnrestorable` (the load event says the document parsed, not that script-built or Mermaid content has rendered), and the chrome retires the stored draft only when a SECOND artifact revision reports that same selector missing. One miss is recorded, not acted on: the element a user annotates is the one the agent is most likely to be rewriting while they type, and an intermediate save that drops it must not delete their notes. Silence is what left an unrestorable draft to be retried against every later load, but retiring on anything less than two revisions is itself data loss. Opening a card cancels the pending settle re-query outright (`showAnnotationCard` -> `cancelPendingDraftRestore`), and the timer also checks `activeCardContext` when it fires: `showAnnotationCard` closes whatever is on screen before it draws, so restoring there would delete text the user is typing that nothing has carried to the chrome yet, and closing that card reports `card: null`, which retires the stored draft - a restore that fired after it would put text the chrome no longer holds back on screen and back into persistence. Retirement is also not silent - `keepRetiredDraft` writes the text verbatim into the page comment thread and persists it under `lavish-axi:retired-drafts:<key>`, so the user keeps a readable copy of writing Hilight can no longer replay; it overwrites nothing they typed and has no control that could discard it. That list is never trimmed to make room: an entry already handed back may not be dropped for a newer one, and a write browser storage refuses is reported in the note itself rather than resolved by evicting an older one.
`reloadChromeAfterServerRestart` must gate the reload on a healthy `/health` answer, never on a deadline alone: reloading into a port nothing is listening on replaces a recoverable page with the browser's own connection-error page, which no Hilight code can undo. A wait that ends on the deadline rather than a confirmed probe re-probes before deciding, because either stale answer is wrong in its own direction.
The "Hilight is not running." card state is **sticky** (`setLayoutGateFailure(..., { sticky: true })`): a later successful artifact load or diagnostic pass clears the ordinary artifact-load failure state but must never clear this copy, because the page is still running the pre-upgrade client against the replacement server and nothing else would tell the user that. A completed pass, manual bypass, or gate timeout must still reveal the artifact; stickiness governs copy, never visual release.
Hand-edited files in `dist/` won't trigger reloads.
Run `hilight server --verbose` (or set `HILIGHT_DEBUG=1`) to log session and watcher events to stderr when diagnosing wedges; detached server stdout/stderr is also appended to `server.log` in `HILIGHT_STATE_DIR` for startup and crash diagnostics.

### Whiteboard (Mermaid → Excalidraw)

At view time the SDK replaces each rendered Mermaid diagram inside a `.mermaid` container with an inline whiteboard: a sibling sandboxed iframe (`allow-scripts allow-popups`, no `allow-same-origin`, `data-lavish-ui`) hosting `/whiteboard-frame`, while the hidden container keeps the Mermaid source authoritative - standalone and exported artifacts render plain Mermaid because the SDK is absent.
Inline frames boot locked in view mode behind a click-catcher so embedded canvases never trap page scrolling; a click unlocks editing, and a Fullscreen action reopens the same diagram in the chrome's overlay (the inline frame parks on `about:blank` meanwhile so two editors never autosave one sidecar).
The frame bundle (`src/whiteboard-frame.js`, built by `scripts/build.js` into `dist/whiteboard/` with Excalidraw, the converter, React, and vendored fonts) converts the diagram with `@excalidraw/mermaid-to-excalidraw` and mounts the editor; flowchart, sequence, class, ER, and state diagrams become editable shapes with Mermaid node/edge ids preserved (`regenerateIds: false`), and every other diagram type becomes an image the user draws on (`imageFallback`).
Frames have no server access: each frame gets a signed, short-lived channel token in its HTML, reports directly to `window.top`, and accepts commands only from that top window; the chrome verifies the token at `POST /api/:key/whiteboard-channel`, binds the frame window and token to its diagram index, then fetches sources (`GET /api/:key/mermaid-sources`, extracted from the artifact file on disk by `src/mermaid-source.js` in `.mermaid` document order) and saved scenes, passes them back over postMessage, and performs all writes.
That channel token is **not** a secret and must never be treated as one: `/whiteboard-frame` has to stay framable by any origin - its legitimate parent is the artifact iframe, whose sandbox gives it an opaque origin that no `frame-ancestors` expression can name - and the frame hands its token to whatever window frames it. Two independent guards carry the trust instead, and both are load-bearing.
Binding: the token is signed over the **session key** (`createWhiteboardChannelToken`/`isValidWhiteboardChannelToken`), so it is a capability for one session only, and `/whiteboard-frame` therefore requires `?key=` and 400s without it; signing `${now}.${nonce}` alone let a token minted with no session named at all authenticate any session.
Descent: the chrome accepts inline whiteboard messages **only from windows whose `parent` is the current artifact frame** (`isArtifactChildWindow` in `src/chrome-client.js`) - descent, not token possession, is what proves the sender is ours; without it, any window that can `postMessage` to the chrome (a popup opener, or a page that framed it) could open a channel and queue a fabricated prompt as the reviewer.
Scenes autosave (debounced) through `PUT /api/:key/whiteboard/:index` into per-diagram sidecar files under `<state-dir>/whiteboards/<key>/` (`src/whiteboard-store.js`) - never into `state.json`, which is rewritten wholesale on every store operation; an authenticated `lavish-whiteboard:flush` performs a bounded save before version-driven chrome reloads.
Whiteboard write routes are same-origin guarded and get a 20 MB JSON limit (`isWhiteboardWriteApiPath`); everything else keeps the 2 MB default.
Staleness is hash-based (`mermaidSourceHash`, or `whiteboardSourceHash` for sources with `%% lavish-icon` lines; see below): a live reload that changes the diagram shows a banner in an open whiteboard. Reopening prompts re-convert vs keep-editing only when the saved scene has preservable edits versus its conversion baseline (`resolveWhiteboardInitAction` in `src/whiteboard-core.js`); an unmodified autosave-on-view silently re-converts. Stale user edits are never silently merged.
"Queue feedback" exports the scene and a PNG server-side (`POST .../feedback-files`), then queues a normal prompt with `tag: "whiteboard"` and an `excalidraw-scene` target carrying a bounded edit summary (diffed from the conversion baseline by `summarizeSceneEdits` in `src/whiteboard-core.js` using the stable ids), local `scenePath`/`previewPath`, `sourceHash`, and bounded stats; poll guidance tells the agent to read the summary first and update the Mermaid source, never the scene file.
The Mermaid source in the artifact stays authoritative; there is no scene→Mermaid reverse conversion.
User-supplied Excalidraw libraries live in `<state-dir>/excalidraw-libraries/`, which Hilight only reads (`src/whiteboard-library-store.js`, size and item caps, skips reported by `hilight libraries`). The chrome fetches them on every whiteboard init (never cached per page, so the frame converts with the same libraries the server hashed into that init's source hash) from the same-origin-guarded, read-only `GET /api/whiteboard-libraries` and passes them in `lavish-whiteboard:init`. Each library snapshot has a `version`, reported by `/api/whiteboard-libraries` and, for sources with directives, by `/api/:key/mermaid-sources` as `libraries_version`; a failed fetch or a version mismatch (a library file changed between the two requests) never blocks the whiteboard: init carries `librariesUnavailable: true`, and when the frame converts a source with `%% lavish-icon` directives under it (`conversionUsesUnverifiedLibraries`), every save of that scene (autosave and queued feedback) keeps the full scene but records the source hash with `UNVERIFIED_LIBRARIES_HASH_SUFFIX` (`createWhiteboardPersistencePayload`), so it can never be restored as matching: a later open re-converts it with the right libraries, or offers the keep-or-re-convert choice when it was edited. A restored scene keeps its saved hash, and a diagram without directives is never marked. Frames still have no server access. Unnamed items are named after their largest text with at least two letters or digits. `toExcalidrawLibraryItems` stamps every library element with `customData.lavishLibraryRef` (Excalidraw keeps `customData` when inserting an item) and groups ungrouped multi-element items, so `summarizeSceneEdits` folds a dropped item into one "Added library item <ref>" line, and reports a library item's moves and resizes from its whole bounds (an icon node's icon relative to its node), and as "Edited library item <ref>" its content edits, any part moved, resized, or reshaped beyond what the item's overall move and scale explain, and deleted parts while others remain ("Removed library item <ref>" only once every part is gone). Generated item refs are unique after normalization, bounds account for `angle`, and an unreadable library file is reported as skipped.
A `%% lavish-icon <node-id> <ref>` comment in a flowchart (`parseLibraryIconDirectives`) turns that vertex into an icon node. The swap happens on skeletons, before Excalidraw materializes them (`prepareLibraryIconSkeletons`): the vertex keeps its Mermaid id, label, and bindings, resizes to hug icon and label, turns transparent, and keeps the normal label size even where the converter shrank it to fit a shape (cylinders). Its bound arrows are extended or trimmed to the new edge, because `convertToExcalidrawElements` binds arrows without rerouting them. Every icon scales to `LIBRARY_ICON_HEIGHT` within `LIBRARY_ICON_MAX_WIDTH` (`libraryIconSize`). Icon nodes grow taller, so a diagram that places an icon gets wider Mermaid spacing only along that axis (`rankSpacing` top-down, `nodeSpacing` left-right; `libraryIconMermaidConfig`): enough that neighbours do not overlap, without spreading the rest of the diagram. `placeLibraryIcons` then adds the scaled item with ids derived from the vertex id (`<id>:icon:<n>`), grouped with the vertex. A missing library, item, or vertex leaves the plain node. Mermaid ignores `%%` lines, so export, share, and direct opens are unchanged. For sources with directives only, `/api/:key/mermaid-sources` folds the referenced items into the hash (`whiteboardSourceHash`), so a changed item re-converts an unmodified scene while every other diagram keeps its plain source hash.

### Boards (canvas mode)

A board is an ordinary artifact: `<main data-hilight-board>` whose `<section>` (or `[data-card]`) children are cards, nested boards as cards that contain cards, all in one file and one session. `src/board-source.js` parses it server-side with parse5; card identity is the `id` attribute, else `card-<n>` in document order, and the SDK's `boardCardIds`/`boardCardOf` must use the same `section, [data-card]` selector and rule.
The artifact route is unchanged: the SDK hides the board's `<main>` at view time and mounts one sandboxed iframe (`/whiteboard-frame?diagramIndex=999&board=1`) over the viewport, so the served bytes still match the file and a direct open still shows the plain grid.
The board frame is a whiteboard frame: same signed channel token, same descent check (`isArtifactChildWindow`), same flush and teardown protocol. Its scene is a sidecar under the reserved index `BOARD_SCENE_INDEX` (999, in `src/board-core.js` and mirrored in `src/chrome-client.js`; a test pins both), so it reuses `PUT /api/:key/whiteboard/:index` and the feedback-files route with no new write path.
`GET /api/:key/board` is read-only, rejects a present foreign Origin/Referer, and 404s a page that is not a board. Code cards read files only inside the code root (the nearest ancestor holding `.git`, else the board's directory), after `realpath`, so a symlink cannot escape it; absolute paths, binary files, and files over 2 MB are refused per card, never for the whole board.
A pin is `data-hash` (sha256 of the range with trailing whitespace stripped, 12 hex) plus a `<pre data-snapshot>` copy, written only by `hilight board stamp`. `stamp` never re-pins a drifted card without `--repin`, so stamping cannot hide staleness. A changed range whose snapshot still appears elsewhere is `moved` and the card follows it; otherwise it is `stale`.
The board revision hashes the file, not the code it points at: a code change refreshes cards in place (`hilight-board:update`, polled by the chrome every 15 s and on focus) without resetting the reviewer's scene, while a file change reconciles the saved scene against the new cards (`reconcileLevelElements`: a reviewer's move survives until the file moves that card, removed cards drop and unbind their arrows).
Cards are Excalidraw embeddables rendered by `renderEmbeddable`. The canvas background is transparent and the embeddable layer sits under the canvas (`z-index: 0`, raised only while a card is active), so reviewer marks draw over cards. Excalidraw admits an embeddable from its `link` once and caches the verdict by element id, and it draws a link icon beside any linked element, so the live scene drops card links after admission while stashed and saved copies keep them.
Code card size is derived, never authored: `sizeCodeCard` (server) sets width from `codeColumns` and height from `codeRows`, and the frame's `CodeBody` and `codeLinesUnder` (mark-to-line mapping) use the same `codeRows`, so a rendered row, the card height and a circled line always agree. `data-w` is only a ceiling (a card may shrink, never grow into a neighbour) and `data-h` is ignored on code cards. Wrapping counts characters at a generous fixed width (`CODE_CARD_LAYOUT.char`), so a row can end early but never clip.
HTML cards render in their own `sandbox="allow-scripts allow-popups"` srcdoc iframes (`buildHtmlCardSrcdoc` in `src/board-core.js`) and never post to the chrome. The srcdoc injects zero-specificity (`:where(...)`) theme-aware defaults (`data-hilight-theme`, `color-scheme`, and light/dark ink/muted/border/surface tokens) before the board's `<head>`, preserves `<html>`/`<body>` attributes (`html_attrs`/`body_attrs`), and applies a layout-only reset that keeps author backgrounds intact rather than forcing `background: transparent !important` (which previously stripped light backgrounds while leaving dark text invisible on dark cards). A self-contained card runtime checks effective contrast against the active canvas backdrop so author-styled dark-text-only or light-background-only cards stay readable in both themes, and posts only measured content height and surface state to `window.parent` (the board frame, verified by iframe `contentWindow` identity and a per-board nonce). For HTML cards without an explicit `data-h` (`auto_h: true`), `applyHtmlCardMeasurements` resizes the card to fit its rendered content (clamped to `HTML_CARD_LAYOUT.minHeight..maxHeight`), reflows unplaced/unmoved cards through `placeLevelCards`, and records the Hilight-chosen rect in `customData.autoRect` while leaving `customData.fileRect` untouched — so reloads preserve reviewer moves, stale cached heights upgrade cleanly, and `summarizeBoardMarks` never reports auto-sizing as a reviewer edit. Threads on cards anchor to `section#id`; the frame reports card viewport rects (`hilight-board:geometry`) and the SDK's `elementRect` substitutes them, so margin threads and the annotation card follow the canvas.
Canvas marks reach the agent as one `board`-tagged page prompt (`board-canvas` target) whose text is `summarizeBoardMarks` output; flow arrows are regenerated from the file on every load and never reported as marks.
Flows are `<ol|ul data-flow>` lists read per level (`parseFlowStep`); legacy `data-to` tokens become one unnamed flow per level. Everything the agent can get wrong (an unknown card, lines outside a card's range, lines on a non-code card, a step that is not a step) lands in `board.problems` as a sentence that names the fix, never a throw, and the board still renders. Layout is derived: text cards in a top grid (at least 3 columns, `ceil(sqrt(n))` for big boards so Fit stays readable), then one band per flow in written order over shared longest-path columns (back edges removed first, so a retry still reads left to right).
Arrows are derived, not saved: `createLinkElements` rebuilds them from the flows and the current card rects whenever `cardGeometryKey` changes, as locked, unbound elements with ids `link:<flow>.<step>`. A line end sits inside the card on that line's row (`codeLineSpan` over `codeBodyTop`, the same geometry `CodeBody` and `codeLinesUnder` use), so a card's note height (`codeNoteHeight`) is part of that shared geometry. `routeAround` is an orthogonal A\* over a visibility grid of every other card inflated by `ROUTE_MARGIN`; `nudgeOverlaps` separates parallel segments of different arrows. HTML cards can only be joined at their edge: their documents are sandboxed and report nothing, so the canvas cannot know where a passage inside them sits.
The board frame owns every wheel event over the canvas (a capture listener on its window): `wheelIntent` turns each into a pan or a proportional zoom with clamped deltas, applied once per frame through `zoomAround`, and Excalidraw's own wheel handler never runs (it zooms linearly and ignores wheels over cards). A pan over a code card goes to its code only while `canScrollBy` says it can still move that way; code scroll offsets feed `createLinkElements` (`scrollOf`), so arrow ends follow scrolled code and pin to its edge. `overscroll-behavior: none` on the board frame and on the artifact document (set by `mountBoard`) keeps a sideways swipe from becoming history navigation.
Geometry sent to the SDK is each card's box clipped to the canvas, so a thread highlight, the annotation card and margin threads never paint outside the canvas. The canvas element itself clips and isolates its cards for the same reason.
One top bar: the board frame has no bar. It posts `hilight-board:header` (level path, summary, `boardHealth`) to the chrome over the authenticated whiteboard channel, and the chrome renders the title, the info popover and the merged status pill. The chrome's comments panel owns the note and **Queue marks**: it posts `hilight-board:queueMarks` and the frame, which owns the scene, exports and answers with `lavish-whiteboard:queueFeedback` or `hilight-board:queueSkipped`; every `queueResult` posted to index 999 settles the button. `controlInsets` measures the floating dock, legend, toast and (only while Draw is on) Excalidraw's tools, so views keep clear of them. The board's own top floaters (the new-card toast) never sit on Excalidraw's top bars: `placeTopFloaters` runs `stackTopFloaters` on every Draw toggle, toast render and resize, putting each 8px below a bar it would overlap and back at rest when the bar goes. A new top floater joins that list (`test/board-input.browser.test.js` checks the rects at 1470x860 and 1116x826).
"New" is computed, never authored: the saved scene's `appState.hilightBoard.known` lists the cards and step signatures (`stepSignature`: flow name plus both ends) the reviewer has seen, `freshSince` diffs the board against it, and `knownAfter` saves everything except what is still unacknowledged. A scene without `known` makes nothing new, so upgrading never flags a whole board. The automatic move to new cards waits for `lavish:artifactShown` (the chrome posts it once per load token when the layout gate is off, and the SDK repeats it to a board frame that starts listening later as `hilight-board:shown`). The gate can cover the board for up to `CHROME_LAYOUT_GATE_CHECK_MS`, so a camera move timed from mount happens where the reviewer cannot see it. A 15 s fallback covers a chrome that never says.
Load time: the SDK's layout audit does not run the ordinary passes on a board (its page is hidden under the canvas and diagram surfaces are never audited). It publishes an empty complete pass as soon as the canvas reports its first geometry (`waitForBoardLive`, capped at `boardAuditWaitMs`), so a board is shown in well under a second. The gated iframe sits at opacity 0.001, never 0: Chromium throttles a fully transparent cross-origin frame to about one animation frame a second, which stretched every gated load to several seconds. A board page never uses the phone layout: the chrome route detects it (`isBoardPage`), links `/chrome.css?layout=desktop` (`desktopOnlyChromeCss` switches the 860px breakpoint off), and `boardPage` keeps `isMobileSheet` false. A board window narrower than 1000px folds the comments margin, at load and on resize, unless the reviewer chose for this session (`"0"`/`"1"` in the collapsed key). The opening view is never saved, so each load picks one for its own window: below `SMALL_CANVAS` it centres the first card of the first flow (else the top-left card) at a readable zoom. A saved view records its canvas size, and `usableSavedView` drops it for a window more than 20% different (or, for an older view with no size, a small window); an untouched restored view is re-picked the same way on resize. The gate records `hilight:layout-gate-revealed` with its reason as a performance mark, so load time is measurable from any browser. Nothing between mount and that first geometry waits on a timer or an animation frame: a window that is not painting runs no frames and holds timers to the next whole second, which put every such load on the gate's cap. The board frame's opening view and first geometry run on message-channel tasks (`afterThisTask`), and a board's layout audit starts without the 50 ms debounce. A phone (`(pointer: coarse) and (any-hover: none) and (not (any-pointer: fine))`, never a width) gets `BOARD_PHONE_NOTE_HTML` instead of the canvas, from CSS alone. `test/board-input.browser.test.js` drives a real board with trusted CDP input (trackpad pans, momentum, spikes, pinch, edge swipes, code-card hand-off, middle-drag, space-drag, the hand tool, shift and ctrl/cmd wheel). Flow-step identity (`stepSignature`) is the flow plus both end cards, never line spans, so re-pinning moved code does not announce new arrows; older saved signatures are normalised. `rememberAutoView` reads the view `setView` asked for, because Excalidraw's `getAppState` still returns the previous view until React commits.

### Image attachments

Annotation image attachments (`src/attachment-store.js`) are content-addressed: the id is `<sha256-of-bytes>.<ext>` and the file under `<state-dir>/attachments/<sessionKey>/` _is_ the identity, so the client never dictates a path or id.
The sandboxed artifact iframe can't reach the loopback server (opaque origin), so the SDK annotation card captures the image, reads its bytes, and hands them to the chrome, which performs the same-origin `POST /api/:key/attachments` (raw body, magic-byte validated - a lying Content-Type is ignored) and reports the server-vetted id back to the card. Upload/delete are same-origin guarded like the whiteboard writes.
Two surfaces originate uploads: that relayed card path and the chrome's own page comment box, whose controller (`createChatAttachmentsController` in `src/chrome-client.js`) owns its chips, send gate, and notice. They deliberately share the page-wide abuse budget below rather than getting per-surface counters. Three invariants keep the composer honest: its notice is DERIVED from item state on every render (`syncNotice`), because an imperatively stamped "waiting for an upload" string outlived the upload it described once that upload failed; paste/drop resolve their payload through the single `transferredFiles` helper, because several browsers expose a pasted screenshot only through `clipboardData.items` and reading `.files` alone attaches nothing with no error and no chip; and the accepted image types come from `ACCEPTED_IMAGE_MIME` (`src/attachment-store.js`, beside the enforcing `detectImageType`), threaded to the chrome through the session JSON and to the card through `createSdkJs`'s `acceptedImageMime` (`acceptedImageTypes`), so both pickers' `accept` attributes, both paste/drop filters, and the composer's rejection copy are derived - a second hardcoded list would let one surface offer a format the others refuse. Like the annotation card, an over-cap file is decided `error` with no retained `file` and no object URL, so it renders no Retry and its bytes are never read.
Four more composer rules are easy to regress: the chip send gate holds back only the composer's own message and an explicit end - queued annotation prompts still deliver (gating the whole `sendQueued` pipeline made Send and Send all and end session silently deliver nothing); paste raises no unsupported chips because Office/macOS pastes expose stray non-image file flavors beside their text (the picker and drop still refuse visibly, and a `Files` drag with nothing enumerable gets an explicit refused chip); the cap counts only uploadable chips (mirroring `currentImageCount`) so a size-refused companion cannot eat a valid image's slot and have `syncNotice` clear the cap notice on the same tick; and a document-level `Files`-drag guard keeps a drop that misses the composer from navigating the chrome away, while leaving text drags to the browser. `planClipboardPaste` (shared rule, duplicated as `keepsClipboardText` in the import-less chrome) treats a pasted file's own name or path in `text/plain` as placeholder, not caption.
The upload route reads the request stream itself via `readAttachmentUploadBody` rather than `express.raw({ limit })`: raw-body aborts on a too-large `Content-Length` WITHOUT draining, which leaves the browser's in-flight upload reset mid-stream so the chip hangs on "uploading" instead of getting the 413. The manual reader buffers up to the cap but always drains to end-of-body, then the route sends a clean 413. Belt-and-suspenders, the chrome also pre-checks byte length against `attachmentMaxBytes` (surfaced in the chrome session JSON) and fails the chip locally before uploading. Do not reintroduce a body-parser `limit` on this route.
Because the sandboxed frame's postMessage source proves origin but not a user gesture, the chrome is the **confused-deputy mediation point** for the relayed card path, and its counters are page-wide, so the composer's own user-gesture uploads spend the same budget: it rate-limits (`UPLOAD_RATE_MAX`/`UPLOAD_RATE_WINDOW_MS`), enforces a per-chrome-session cumulative-byte quota (`UPLOAD_SESSION_BYTE_QUOTA`), AND bounds concurrent in-flight uploads (`UPLOAD_MAX_IN_FLIGHT`, D8 - rate + cumulative alone let ~30 large bodies fetch at once before the quota tripped) before any upload reaches the loopback server; over-cap uploads are refused with a retry hint and a settled upload frees a slot. The server keeps a bounded default disk quota (`DEFAULT_MAX_ATTACHMENT_DISK_BYTES`) as the durable backstop.
The **trust boundary** is `SessionStore.queuePrompts`: a queued prompt carries only the client's `id` + display `name`; `resolvePromptAttachments` re-derives every authoritative field (absolute `path`, mime, bytes, dimensions) from disk via the injected resolver, so a crafted `/prompts` POST cannot aim an attachment at an arbitrary file. Repeated content ids remain repeated logical references with their own display names and count separately toward prompt count/byte caps; content-addressed storage deduplicates only the bytes on disk. Resolution is **all-or-nothing** (C4): a malformed field/entry, any unknown id, or a count/byte-cap breach rejects the whole batch (`{ rejected, caps }`, persist nothing → 400), never a silent partial-drop; the chrome keeps its queue on the 400 and surfaces the reason. User-facing limits/env vars and defaults are owned by README's Image attachments bullet.
`boundAttachmentRefs` runs BEFORE the resolver and is why a crafted batch can't wedge the server: the in-resolver cap counts RESOLVED refs, and a well-formed id for a file that doesn't exist never advances it, so thousands of them would each buy a sequential `stat` while the store's single mutex is held, stalling every poll and mutation. Raw per-prompt and request-wide (`MAX_REQUEST_ATTACHMENT_REFS`) counts are rejected up front - except that a closed-poll restore is exempt from the request-wide bound alone, for the reason given in Request flow step 7 - and the reported rejection list is capped (`MAX_REPORTED_ATTACHMENT_REJECTIONS`) so the 400 can't be turned into an amplifier. New pre-resolve validation belongs in that same pure gate - never after the first `await` into the filesystem.
`SessionStore` owns ONE `AsyncMutex` (`src/async-mutex.js`, `store.lock`) covering BOTH concerns. Every `state.json` read-modify-write runs under it - `queuePrompts`, `takeFeedback`, `recordLayoutWarnings`, `upsertSession`, `endSession`, `addAgentReply` - so a poll can't clear prompts in the window `queuePrompts` holds its pre-resolve snapshot and then clobber the take (E1); **any new store mutation must acquire this lock too**. The server routes its attachment disk sections (upload finalize, delete, the sweep) through `store.runExclusive` so they share that same lock, keeping the reference snapshot + delete atomic against `queuePrompts` (D5). `referencedAttachmentIds` is a pure read and must stay lock-free - the server calls it from inside `runExclusive`, so self-locking would deadlock. Delete is **reference-counted** under the lock - a content-addressed file shared by a queued prompt survives a DELETE request (`status: "referenced"`) - and dedup re-upload **refreshes the mtime** so a re-referenced aged file isn't reaped by the next sweep (B3).
Dimensions are persisted at upload in a `<id>.meta` sidecar (D6): `resolveAttachment` reads it instead of re-parsing the whole image, and the thumbnail GET uses `statAttachmentForServe` (one stat + streamed send, mime from the id extension) instead of a second full read. Sidecars are removed with their image on delete/sweep and are excluded from `listAttachments` by `ID_RE`.
The SDK's annotation card gates queuing on BOTH `hasPending()` (R2.4, an in-flight upload) AND `hasErrors()` (W2, a failed/rejected chip) so neither is silently dropped by `collectReady`/`closeCard` - it keeps the card open with a notice so the user can wait, retry, or explicitly remove; that notice line is shared with the card's neutral keyboard hint, so it renders in the error color and is restored (never left stale) once the condition clears. A count-cap rejection remains visible while the card is full and clears only when removing a chip creates capacity. A mixed drop **partial-accepts**: `partitionDroppedFiles` always reports both halves, so the images attach AND every unsupported companion raises its own `UNSUPPORTED_TYPE` chip - reporting the unsupported files only when no image was found is what made a mixed drop swallow them silently. Removing a chip deletes **nothing**: there is deliberately no `lavish:removeAttachment` message and the chrome honors no iframe-driven delete, because the iframe is untrusted and no client can see every live reference (attachments are content-addressed, so another tab's ready-but-unqueued chip shares the id and is invisible from here). Only the reference-aware sweeper and the reference-counted same-origin `DELETE` route remove unreferenced attachments; the chrome never drives the latter, so do not reintroduce an eager delete. Upload results are scoped to the document that asked for them: each document mints an `ATTACHMENT_NONCE`, sends it with every upload, and `isTrustedAttachmentResult` requires both an exact nonce match and `event.source === parent` - chip ids restart at `att-1` on every load, so id alone would let a result in flight across a reload mark a new chip with the previous document's image. The card's per-prompt count cap is NOT a literal: `createSdkJs` threads the server's `maxPerPrompt` into the SDK so the local guard matches `HILIGHT_MAX_ATTACHMENTS_PER_PROMPT` (W1), and an over-cap pick is surfaced instantly rather than swallowed. Queued and sent note bubbles always render at most four thumbnails and collapse every additional attachment into an explicit `+N` badge, independent of that configurable cap (`test/chrome-client-queue.test.js`). The card re-clamps its viewport position after every attachment-row render (W3) so chip rows can't push Queue/Cancel off-frame; the chip list also has a `max-height`/scroll backstop.
Cleanup (`sweepAttachments`, run at server startup + hourly) is **reference-aware** and never removes a file in `SessionStore.referencedAttachmentIds()`. It has two distinct passes: TTL cleanup reaps an unreferenced file once it is past its TTL (`HILIGHT_ATTACHMENT_TTL_MS`, seven days by default), and cap eviction, under disk-cap or object-cap pressure, removes unreferenced files oldest first before their TTL, but only once they are older than `ATTACHMENT_EVICTION_GRACE_MS` (one hour) - so a send-and-end batch's images are never lost before delivery, and orphaned uploads (card cancelled, or `/prompts` never followed) are reaped later.
That reference set is pending-prompt ids **plus** ids delivered within `ATTACHMENT_DELIVERY_GRACE_MS`: `takeFeedback` clears the delivered prompts, so without that window an attachment would become sweepable at the exact moment the agent starts reading the path it was just handed. The grace is a bounded read window, not a second lifetime (the TTL and disk cap must still reclaim delivered bytes eventually), and the retained list is capped (`MAX_DELIVERED_ATTACHMENTS`) because it lives in `state.json`, which is rewritten wholesale on every store operation.
The eviction grace is the symmetric window on the upload side (fixed, not env-tunable): "unreferenced" also describes a **ready chip** - an image sitting in an open annotation card or the page comment box that has not queued a prompt yet - so cap eviction with no age floor deletes bytes out from under the imminent Send, which then fails unrecoverably as not-found. It never lets the total exceed the cap, because admission refuses the new write instead.
The disk cap charges **allocated** cost, not logical image bytes: `listAttachments` reports `chargedBytes` = the image rounded up to whole `ATTACHMENT_ALLOC_BLOCK_BYTES` (4096) blocks plus the sidecar's own block, and both of its enforcement points measure `maxDiskBytes` against that accounting. Summing logical `size` let a flood of 12-byte magic-prefix uploads (the smallest `detectImageType` accepts) sit ~683x under the reported total while consuming real disk and inodes.
The periodic sweep is only one of those two points, and it can never hold the cap alone: it refuses to evict referenced or in-grace files, so concurrent chrome pages could each write past `maxDiskBytes` in the window before the next sweep. `admitAttachmentCharge` inside `writeAttachment` is therefore the single **upload-admission chokepoint** every byte-adding write path must route its charge through (today a new image+sidecar and the dedup sidecar repair; the dedup mtime rewrite replaces identical bytes and the sweep only removes): it reclaims toward `cap - newCharge`, measures the true committed allocation with its own tree walk so the undeletable temp/orphan debris a curated survivor set hides is still counted, and refuses with **507** when the write would not fit. Admission must run under the store's lifecycle lock so the reference snapshot, the reclaim, and the write are one critical section; a refused sidecar repair is skipped (the sidecar is only a display cache) rather than failing the dedup upload. The `maxObjects` bound is **derived** from the disk budget (`budget / 2 blocks`), never a separate env var, so it can only agree with the byte cap. The sweep's cap/object eviction keeps **running totals** decremented per removal rather than recomputing over all survivors per candidate: it runs under the store's global mutex, so per-candidate O(n) work would be an E3-class lock hazard. The sweep also reaps files that `ID_RE` hides from every cap: crash-orphaned temp files (D6) - `writeFileAtomically` writes `<name>.<pid>.<n>.tmp` then renames, and a crash in between leaves one, reaped once older than a 5-minute grace (a live write renames within ms) - and orphan `<id>.meta` sidecars whose image is gone (ATTACH-002), reaped with no grace since a live upload writes the image before its sidecar. `removeAttachment`/`removeFile` delete the sidecar FIRST, so a crash between the two removals leaves only the counted image, never an uncounted orphan sidecar. The SDK decides a whole drop in one pass via the pure `classifyAttachmentBatch` (mime / size / count-cap per file) and `addFiles` renders **once** instead of per file (D7 - a large multi-drop was O(N²) DOM rebuilds); `rejectUnsupportedBatch` does the same for unsupported files. The size decision lives in that classifier and still runs **before** `createObjectURL`/`arrayBuffer` (`attachmentSizeError`, threaded from the server via `createSdkJs`'s `maxAttachmentBytes`), so an oversized drop is decided `error` and never read into a buffer or structured-cloned into the chrome; the server still re-checks.
Attachment files and dirs are created **owner-only** (`0600`/`0700`, set explicitly at creation since the umask would otherwise leave 0644 in traversable dirs) and `ensureAttachmentDir` re-asserts the dir modes so an install that uploaded before that hardening doesn't keep its existing screenshots exposed. A dedup upload's mtime refresh is load-bearing (it restarts the TTL clock) and must never be swallowed into a success: `writeAttachment` falls back to an atomic rewrite of the identical bytes and propagates if that fails too. Env limits floor BEFORE the bounds check and require `>= 1`, so a fractional `0.5` falls back instead of flooring to a silent zero cap; only `0`/`off` may disable one.

<a id="export-local-asset-inlining"></a>

### Export (local-asset inlining)

`src/export-bundle.js` (`buildSelfContainedHtml`) inlines only an artifact's **local** assets: local stylesheets/classic scripts become inline `<style>`/`<script>`, and local images/fonts/icons, confined fetchable `file://` refs, and CSS `url(...)`/`@import` become data URIs (recursively, resolved relative to each stylesheet).
Remote references are deliberately left as links; the user-facing contract, including the size-cap env vars and their defaults, lives in README's Export and sharing bullet.
The transform makes **no outbound requests** (no fetching, no SSRF); its only security surface is local file reading, which is confined to the artifact directory both lexically (`confineDir`) and by **real-path/symlink resolution** in the default `readLocalFile` (`guardedRead`), so a symlink inside the directory can't exfiltrate an outside file (e.g. `~/.ssh/id_rsa`) into a shared bundle.
Absolute `file://` paths in non-inlined regions are redacted to `about:blank` so local paths do not leak into exports or hosted shares; the injected Hilight SDK is stripped; in-document fragment refs (`#a`, encoded `%23a`) are left alone; and inlined `</script>`/`</style>` are escaped so they can't break out.
The transform records `warnings` rather than failing, split into unresolved local assets (such as `load-failed`, `outside-root`, `too-large`, or unsupported local references left external) and notices (such as `csp-meta` or `file-url-redacted`).
It is dependency-injectable (`readLocalFile`, `resolveAbsolute`, `confineDir`, size caps) so it is testable without disk; the server passes `resolveAbsolute: resolveDesignAssetPath` to inline legacy `/design/*` references from the packaged assets.
The chrome's **Export standalone HTML** overflow-menu item `GET`s `/api/:key/export`; the CLI exposes the same transform as `hilight export`, server-independently.
Hilight sends two `Content-Security-Policy` headers, and neither restricts which assets artifact content may load: the chrome page answers `frame-ancestors 'none'`, and every `/artifact/*` response carries only the `sandbox` directive matching the iframe's `sandbox` attribute, so an escaped popup stays opaque-origin (see [Things to know when editing](#things-to-know-when-editing)). Exports and hosted shares carry neither header. Author-set CSP meta tags are preserved and reported as export notices because they may still block exported inline assets.

### Hosted sharing (ht-ml.app)

`src/html-app.js` (`publishToHtmlApp`) publishes the local-inlined HTML to the share backend `HILIGHT_HTML_APP_API_URL` names, defaulting to ht-ml.app.
The wire contract - endpoint, request body, required response fields, and the optional bearer token - is owned by [docs/self-hosting-share.md](self-hosting-share.md); do not restate it here.
What matters architecturally is that creating a site needs no account or API key, so the response's secret `update_key` is the only credential the user ever gets and it is returned once.
The user-facing contract - third-party disclosure, public by default, private with a password - lives in README's Export and sharing bullet and the runtime share output.
The browser's **Publish link** flow `POST`s `/api/:key/share`; the route is **same-origin guarded** (`isSameOriginRequest`) because publishing is a state-changing, outward-facing action - a cross-origin page must not drive a publish through the loopback server.
ht-ml.app serves hosted pages with no CSP and no sandbox header, so remote CDN/font references load over the viewer's network; hosted shares never include the annotation SDK.
Share passwords are **generated in one place** (`src/share-password.js`) and reach the browser through the `/api/:key/share` response, because `src/chrome-client.js` is served as a raw file and cannot import modules: a browser-side generator would be a second copy of the alphabet and length rules, free to drift from the CLI's. That route echoes a password only when it minted one - a password the user typed is never sent back - and Hilight persists neither it nor the `update_key` anywhere, so `state.json` never becomes a store of hosting credentials.
The host has **no delete endpoint** (`GET`/`PUT` only on a site), so `--unpublish` is a `PUT` of a placeholder page behind a discarded random password. It is not a deletion, the URL still resolves, and every surface has to say so; a flag or a next_step that claims a published page was removed is a lie the user acts on.
The `PUT` password semantics are **probed against the live host, not inferred**, and the evidence lives in a comment on `createHtmlAppUpdatePayload`: omitting `password` preserves the page's current one and sending a new one rotates it, but sending `""` answers 200 and changes nothing. So there is deliberately **no clear-password path** - the host documents a clear it does not perform, and a surface reporting a page as public while it is still gated is the same class of lie as calling `--unpublish` a deletion. Re-probe before adding one back.
Every request that changes hosted state classifies its own failure through `hostRejectedShareWrite` (`src/html-app.js`, shared by the CLI and the browser `POST /api/:key/share` route): only a 4xx proves the host wrote nothing, so a 5xx, a transport failure, or a timeout must be reported as an outcome that may already have landed. A 200 whose body is missing required fields is neither - the page landed - so `publishToHtmlApp` throws through `htmlAppIncompleteResponseError` carrying whatever fields did arrive, and the caller reports a SUCCESSFUL publish rather than hedging. A site_id the host echoes is untrusted (`echoedSiteId`) and never reaches a suggested command; those interpolate the locally validated id. A republish and `--unpublish` say the change may already be live and name a re-run that converges; a CREATE cannot, and says so - the lost response held the only copy of the update_key, so a page that landed that way can never be republished or unpublished, and re-running mints a second page instead of reclaiming the first. Never offer that path a recovery it does not have. Whether Hilight minted a password is NOT what decides that: a generated password is an extra hint layered onto the indeterminate report (a rejection must never carry it, since it gates nothing), never its trigger. Any new path that changes a published page needs the same split, and every command string those errors suggest is built by `republishCommand`/`unpublishCommand` so a recovery hint cannot drift into a shape `resolveShareRequest` rejects. Those commands must never contain a password placeholder: every other placeholder fails loudly when pasted literally, but any non-empty string is a valid password, so a literal `<pw>` would rotate a live page to a secret nobody was told and the host cannot clear it. Name `--private` (it takes no value) or describe the password in words.
An empty or whitespace-only value for one of share's value flags is **refused**, never treated as absent: the host reads an empty password as none, so `--password "$PW"` with an unset variable would publish a PUBLIC page the caller believes is gated (README's `--password` row and the `share` help own that contract).
Setting a password takes effect at the origin, but the **public -> private transition is not instant at the CDN edge** - a page that was public kept answering uncredentialed requests for minutes afterwards. That is a property of the transition, not of the command performing it, so every surface reporting a page as newly gated carries the caveat (today `createShareUpdateOutput`'s private branch, `createShareUnpublishOutput`, the `share` help, and README's Export and sharing bullet); a page that was already private has no such cached copy. It is deliberately absent from the home/skill guidance, which every run pays for.

### AXI integration

The CLI is built on `axi-sdk-js` (`runAxiCli`).
The `home()` callback returns the rich object shown when the user runs `hilight` with no arguments - the same TOON-serialized output that lands in the agent's optional `SessionStart` hook after `hilight setup hooks`; top-level `--help` prints only `createTopLevelHelp()` (commands and the loop, under 2 KB), and `--help --full` returns the static home guidance without dynamic sessions. Per-command `--help` comes from `SHORT_COMMAND_HELP` where one exists and from `createCommandHelp` with `--full`.
Every command's flags are listed in `COMMAND_FLAGS`; `withFlagCheck` refuses any other flag with `VALIDATION_ERROR` (exit 2) before the handler runs. A new flag goes into that table, or the command refuses it.
`hilight --version` is answered in `bin/hilight.js` from the leaf `src/version.js` before the CLI is imported. The build splits `dist/cli.mjs` from lazily imported chunks that sit beside it in `dist/`, because the CLI resolves `server.mjs` and its assets from `import.meta.url`; never move chunks into a subdirectory.
Poll execution guidance is shared across home output, help, and `next_step` responses through `POLL_WAKE_PATH_RULES`: every agent gets the same wake-path contract in plain shell terms (no harness vocabulary), while `detectInvokingAgent` adds an attached-turn warning when `CODEX_SANDBOX` or `CODEX_THREAD_ID` identifies Codex. The installable skill does not restate these rules; it points at `hilight --help`.
Agent-facing design guidance is single-sourced in `src/design-reference.js`: `DESIGN_PRIORITY_RULE` states the design-direction priority order exactly once, and `DESIGN_SYSTEM_HINT`, the `hilight design` summary, and the design command help all embed it - never restate the rule on another surface (README carries only a one-sentence summary). The skill points at `hilight design` instead of embedding the rule.
`src/skill.js` renders the minimal installable Agent Skill, a stub (under 1 KB of body) that points at `hilight --help`, which routes to every other command and to `references/using-the-page.md`. It retains the non-interactive `npx -y <release tarball>` fallback and slash-command request handling, omits live session state and author credit (that lives in LICENSE and the README fork note), and includes Hermes Agent frontmatter metadata for categorization.
The generated skill intentionally omits a `version` frontmatter field because release-please updates `package.json` without regenerating `skills/lavish/SKILL.md`.
`skills/lavish/SKILL.md` is the only public Agent Skill shipped through npm.
The repository-local `.agents/skills/lavish-design/SKILL.md` brand skill is internal and must keep `metadata.internal: true` so `npx skills add ... --list` and skills.sh hide it unless `INSTALL_INTERNAL_SKILLS=1` is set.
The bare-arg form (`hilight some.html`) is normalized into `["open", "some.html"]` by `normalizeArgv`, which must let the SDK's `RESERVED_COMMANDS` (such as the built-in `update` self-updater) pass through untouched; otherwise the bare-arg rewrite turns `hilight update` into `["open", "update"]` and the inherited reserved command never reaches `runAxiCli`.

### Agent Plugins packaging

The published package root **is** the Agent Plugin: `plugin.json` sits beside the `skills/` directory the standard discovers, so an installed copy is a conformant plugin with nothing downloaded and no marketplace involved (README's Agent Plugin bullet owns the user-facing contract). Keeping that true is the invariant - both `plugin.json` and `skills/lavish` must stay in `package.json` `files`, and `resolvePluginRoot` resolves `../` from `src/plugin.js`, which is the package root when bundled and the repo root from source.
Agent Plugins delegates skill validity wholesale to the Agent Skills spec and **silently skips** skills that fail it, so a frontmatter regression removes the skill from the plugin with no error anywhere. `validateSkillMarkdown` (`src/skill.js`) encodes the rules the reference validator enforces: only `ALLOWED_SKILL_FRONTMATTER_KEYS` at the top level, no YAML flow collections (`[a, b]`), and `metadata` limited to one level of string values. That is why `author` and `argument-hint` live under `metadata` and the Hermes fields are flattened rather than nested - moving any of them back to the top level silently invalidates the skill.
Each client registers independently and a client that cannot be registered must be _reported_, never thrown: `linkCursorLocalPlugin` returns `unsupported` instead of raising so one unlinkable client cannot abort the command or the other clients. On Windows it prefers a **junction**, because a directory symlink there needs a privilege an ordinary account lacks (Developer Mode or elevation), then falls back to a directory symlink when the junction is refused, such as across volumes. Tests that assert on a real on-disk link skip when symlink creation is unavailable; the link-creation logic itself stays covered everywhere through injected operations.
`setup plugin` registers only clients that install from a local path (VS Code, Cursor, Copilot CLI); Codex installs from marketplace sources only and is deliberately served by the SessionStart hook instead. Registration follows the same discipline as `setup hooks` - explicit invocation only (issue #43), idempotent, and path-repairing - and `isStalePluginLocation` only ever drops entries it can positively attribute to this plugin, so a user's other plugin locations survive. VS Code settings that fail to parse (they legally allow comments) are reported for manual edit, never rewritten.
No `mcp.json` ships: the CLI itself is the agent interface, and adding one would create a second agent-facing contract to keep in sync.

### Telemetry

`src/telemetry.js` posts anonymous events to an Umami endpoint.
The website ID and host can be baked into the bundle at build time via `HILIGHT_UMAMI_HOST`/`HILIGHT_UMAMI_WEBSITE_ID` env vars (consumed by `scripts/build.js` and inlined as `process.env.LAVISH_AXI_BUILD_UMAMI_*` defines).

The client is best-effort and must never affect CLI behavior - all errors are swallowed.

### Event log and traceability

Hilight serves the user and the agent, and both need to know what happened after the fact, so the server keeps one event log: `server.log` in the state directory (`src/event-log.js`), one line per event, `<ISO time> <session key or -> <event> <cause>`. The server writes it itself with synchronous appends, whatever started it (the CLI, systemd, a terminal), so a stop line is on disk before the sockets close or the process exits. It is appended and never truncated; it rotates at `EVENT_LOG_MAX_BYTES` into `server.log.1` and `server.log.2`. A detached server's stdio goes to the same file; those lines never parse as events and readers skip them. Logging never throws.

- `serverCommand` turns SIGTERM, SIGINT and SIGHUP into `server.stop(cause)`. Without that, a supervisor stop exited with no line and the reason a poll died was gone (an empty `server.log` after a restart).
- `shutdown` writes a `listen-end` line naming the stop for every active poll, then `server-stop`, then closes sockets. The `listen-end` handler never relabels those polls as "disconnected".
- Every way a poll stops listening goes through `releasePollListener`, which emits `listen-end` with `holder.endReason`. `listen` and `listen-end` lines are written only for polls that entered the wait, so an immediate delivery logs `delivered` alone.
- At startup the server reads the recent log: `previousServerExit` names why the server before it went away (or that it left no line), and the last `listen-end` per session seeds `listenEnded`. A `listen` with no end becomes "the server stopped (...)". The `agent-presence` event carries `since` and `why` when the state is `waiting`, and the chrome shows them; it never invents a reason.
- `hilight poll` reconnects after a lost connection for `POLL_RECONNECT_WINDOW_MS`. For the first 3 seconds it only probes, so a supervisor's own server wins the port. A request that carried a reply and failed before any answer is reported, not retried, because it may have landed; once the server answered, a retry only listens again (`reconnect=1`, logged as such).
- `GET /api/:key/history` (the page's Activity list) and `hilight status`/`hilight log` only read. History refuses a foreign Origin like `/review`. `hilight status` never starts a server.
- CLI errors render through `formatTraceError`: the SDK's `error`, `code`, `help`, plus `why` and `log` when known. `toonString` follows TOON's own quoting rule so an error without them renders byte for byte as before.

## Things to know when editing

- `run()` short-circuits `--version`/`-v`/`-V` (`isVersionOnlyArgv`) before `ensureStateDir` and `initDefaultTelemetry`, because agent harnesses probe every tool's version at session start and the telemetry drain in the `finally` block costs up to a full second. Any new startup work must go after that short-circuit; `test/cli-version.test.js` guards both the latency budget and the "no telemetry request, no state dir" property.
- `canonicalFile` runs `realpath`, so symlinks resolve to their target before becoming session keys. Two paths that refer to the same file always collapse to one session.
- The SDK injected into artifacts lives in `src/artifact-sdk.js` and is wrapped by `createSdkJs`.
  It executes inside an iframe sandboxed with `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox allow-downloads` (no `allow-same-origin`), so it cannot read the chrome's DOM - communication is `postMessage` only - and it runs the layout audit in the iframe because the chrome cannot directly inspect the sandboxed document. `allow-popups-to-escape-sandbox` lets popups render as top-level tabs without weakening the artifact iframe. Every `/artifact/*` response also carries the matching CSP `sandbox` policy, so an escaped popup that navigates to an artifact-owned active document remains opaque-origin and cannot become a same-origin application client.
  EVERY artifact→chrome message must go through `postArtifactMessage`, the only send path that stamps the current `artifact_load_token`: the chrome's message listener drops any frame message whose token is not the current load's before dispatch, so a raw `parent.postMessage` is silently discarded (a token-less `lavish:uploadAttachment` shipped exactly this break while every mocked harness stayed green - the chrome harness must therefore send test messages verbatim, never patch the token in).
  Nothing (Tailwind, DaisyUI, Mermaid, layout safety CSS) is auto-injected into artifacts; agents choose a design direction via the single-sourced `DESIGN_PRIORITY_RULE` (see AXI integration above).
  The `hilight design` Mermaid snippet chooses dark or light rendering from the effective artifact page background and re-renders when a page-theme or OS appearance change alters that appearance, so do not hardcode one Mermaid theme.
- For rendered Mermaid SVGs outside `.mermaid` containers, the injected SDK retains dependency-free viewBox pan (drag) and zoom (wheel) in explore mode, then freezes it in annotation mode so a click resolves cleanly to one node instead of panning. It enhances on load and `DOMContentLoaded` and re-runs through a throttled `MutationObserver` because Mermaid renders asynchronously and can re-render. Enhancement touches only the live SVG's `viewBox` and listeners, never the saved artifact, so the diagram still renders identically when opened directly. Node detection, label extraction, and target validation live in `src/mermaid-node.js` so they are unit-testable and shared with the server.
- Any helper `createArtifactSdk` calls must reach the browser through `serializeModuleHelpers` in `createSdkJs`, which turns every export of a shared module (`src/mermaid-node.js`, `src/table-cell.js`, `src/artifact-revisions.js`) into a same-scope `const`. A module-private function called from the SDK closure compiles fine and only `ReferenceError`s on the first click, so put new helpers in one of those wholesale-serialized modules and export them; a helper may then reference only its own arguments, browser globals, or its sibling exports - never a module-level constant, which is not serialized. Those modules must export functions and nothing else: only functions survive `toString()`, so `serializeModuleHelpers` throws on any other export rather than shipping a `Set` or `RegExp` that would arrive as an empty `{}`. `test/artifact-sdk-bundle.test.js` boots the served bundle and drives a real click, which is what catches an unreachable helper; the module-level unit tests cannot.
- Table-cell annotations attach `src/table-cell.js`'s semantic row/column names as `target` only. The clicked element's own `selector`, `tag`, and `text` keep describing that element, because the on-screen highlight outlines exactly what was clicked. Both coordinates stay silent rather than name a row or column they cannot prove, because a confidently wrong name reads as authoritative and is worse than none: a rowspan is clipped to its own row group, so only one starting in an earlier row of that group (including `rowspan="0"`, which runs to the end of it) makes a row's DOM order stop being its rendered order, and that suppresses the row's positional heading - only a declared `scope="row"` heading survives it - while the column label needs the header row unshifted the same way, plus a row whose colspans sum to the header's and a cell that does not straddle a grouped header.
  A grouped header's `<th rowspan="2">` therefore costs the leaf header row its names and leaves every `<tbody>` row nameable.
  Spans come from the browser-parsed `rowSpan`/`colSpan` whenever present, because HTML's integer rules stop at the first non-digit and render `rowspan="2x"` as a real two-row span that `Number` reads as `NaN`. Resolving a cell walks its whole table, so `context()` computes the target only under `{ table: true }`, which the annotation card passes and `snapshot()` - which calls `context()` for every element in the document - deliberately does not.
- Annotation handlers ignore native controls (`button`, `input`, `select`, `textarea`, `option`, `label`, `summary`, editable regions, and elements with an interactive ARIA widget role such as `role="button"` or `role="menuitem"`) and their descendants, so they stay interactive without markup; an `<a href>` stays annotatable when it carries such a role or sits inside such a widget, because a passed-through click would navigate the artifact frame away; `data-lavish-action` opts custom non-native controls out of annotation and gives them a pointer cursor. Artifact-author guidance for input patterns (`data-lavish-question`, `queueKey`, per-question submits) is owned by the input playbook in `src/playbooks.js`.
- For text annotations, `prompt.selector` is the common ancestor/container selector, not the complete identity. Use the `target` range boundaries and snapshot context to locate the exact selected text.
- For non-whiteboard Mermaid diagram nodes, a click annotates the whole rendered `<g>` node - not the sub-shape under the cursor - and hover highlights the same node. `SessionStore.normalizeTarget` routes these targets through `normalizeMermaidNodeTarget`, which strips them to the fixed `type`/`diagramId`/`nodeId`/`label`/`selector` shape, while text-range and other/legacy targets pass through unchanged.
- `SessionStore` re-reads and re-writes the entire `state.json` on every operation - there is no in-memory cache. The single server process is necessary but NOT sufficient for consistency: a method that reads state, `await`s, then writes can still interleave with another method's read-modify-write and lose its update. Every mutation therefore serializes through the store's single `AsyncMutex` (`store.lock`); see the Image attachments section (E1) for the full invariant and the one lock-free exception (`referencedAttachmentIds`).
- Below 860px the comments margin (`aside.comments`) is a fixed bottom sheet with a persistent dock (the phone block in `src/chrome.css`; README's Reviewing on a phone bullet owns the user-facing behavior), and the chrome's sheet controller in `src/chrome-client.js` owns open/closed intent, `inert` on the hidden half, focus handoff, gestures, visual-viewport synchronization, and the dock summary. `MOBILE_SHEET_MEDIA` there must match the CSS breakpoint. Four rules are easy to break: the phone block must come after the comments rules in `src/chrome.css`, because it overrides their absolute margin positioning with a stacked list and the cascade decides the winner; the collapsed state is a `translateY`, never a height change, so the threads keep their layout and the sheet can follow a drag, which is also why the phone sheet carries a shadow hairline instead of a border (a 1px border pushes the docked head past the viewport edge); the sheet is sized from `--vv-top`/`--vv-height`, which `syncVisualViewport` keeps equal to the visual viewport, so the iOS keyboard shrinks it instead of covering a reply box (Android gets the same through `interactive-widget=resizes-content` in the viewport meta, and `viewport-fit=cover` is what makes the `env(safe-area-inset-*)` padding non-zero); and `positionThreads` clears every transform and compact class while `MOBILE_SHEET_MEDIA` matches, so the stacked list never inherits desktop margin offsets. Real geometry is pinned by the opt-in `test/mobile-conversation-sheet.browser.test.js`.
- The chrome and the sandboxed artifact document cannot see each other's keyboard events (no `allow-same-origin`), so any keyboard shortcut that must work regardless of focus needs its own capture-phase `document.addEventListener("keydown", ..., true)` in _both_ `src/chrome-client.js` and `src/artifact-sdk.js`, not just one.
  The annotate/explore mode toggle hotkey (`MODE_TOGGLE_HOTKEY_KEY`, Cmd/Ctrl+I) is the reference implementation: the SDK initializes from `data-lavish-annotate` on the root html element (only `"off"` disables), and reports that default once with token-stamped `lavish:annotationMode`. The chrome accepts one boolean default per artifact load until the reviewer explicitly toggles, then keeps that choice across artifact reloads and reconciles it back to the SDK, including when frame-load replay arrives before the default report. On catching the hotkey the SDK sends `{ type: "lavish:toggleAnnotationMode" }` to the chrome, which drives the exact same `toggleAnnotationMode()` function the on-screen switch's `onclick` calls.
  Requiring a modifier (`metaKey || ctrlKey`) is what lets the listener safely call `preventDefault()` without breaking plain typing (including typing the bound letter itself) in the chat box or an annotation-card textarea.
- Tests use `HILIGHT_STATE_DIR` and ephemeral ports to stay isolated. When adding tests that spin up the server, do the same.
- Circular close buttons (`.queued-remove`, `.share-close`) render an inline SVG x mark with two symmetric strokes, not a text `x`/`&times;` glyph.
  Font metrics put text glyphs off from the geometric center even under flex centering, while the SVG centers via flex plus equal viewBox margins.
  Keep the SVG strokes on `currentColor` so existing hover color rules still apply, and follow this pattern for any new circular icon-only button.
- The in-iframe layout audit (`src/artifact-sdk.js`) is severe-only and fails open on uncertainty; its easy-to-reintroduce failure modes are covered by dedicated and browser-level tests:
  - Scroll dimensions and parent overhang are never proof by themselves. `classifySevereTextOverflow` requires rendered text-range fragments from one semantic text boundary to materially cross that boundary, excludes explicit truncation, masks, and standard visually hidden text, and reports vertical loss only when a line's center leaves its box.
  - Diagram surfaces (`.mermaid`, SVG, and `[data-lavish-ui]`) stay outside the general audit so it does not compete with the separate Mermaid and Excalidraw diagram-label clipping path.
  - Page overflow requires both a material document delta and meaningful text or required-control bounds beyond the usable viewport, producing one `html` root finding instead of descendant geometry noise.
  - Finite animations settle before sampling, findings associated with still-active finite or infinite motion stay silent without hiding independent stable failures, and `findStableLayoutFindings` requires the same severe root in two samples.
  - Overlap reports only near-total coverage by one opaque static sibling; decorative transparent overlap stays silent. Warning-severity input is filtered again by the chrome and by `normalizeFindings` in `src/layout-warnings.js`.
  - The audit reports its own completeness. A failed run must publish `complete: false` with no findings, never an empty completed pass - an empty completed pass is read as evidence of repair, so the distinction is what keeps a crashed audit from silently resolving real warnings.

- The self-paint check (`src/self-paint.js`, surfaced by `open`/`export`/`share` as `self_paint_warning`) is render-free and fails open by design: any stylesheet link, `@import`, Tailwind runtime script, `color-scheme`, or html/body/:root background signal suppresses it, because a false warning on every open is worse than a miss from this intentionally conservative static check. Keep it a warning - never a blocked open, never auto-repair.

- The chrome page ships from `createChromeHtml` with the layout-gate overlay ALREADY covering the artifact area. `CHROME_BOOT_FAILSAFE_JS` is inlined BEFORE the `<script src="/chrome-client.js">` tag (a request that hangs rather than errors blocks parsing, so a failsafe placed after the tag would never be reached), installs the shared gate escape before the client can fail, and handles the script's `onerror` and boot timeout. The client reuses that escape and cancels only the boot-failure timer by setting `window.__lavishChromeReady` at the very end of the file. Keep the placement, timeout, end-of-file cancellation, ended-session guard, bounded gate hold, and network-independent **Show anyway** path: the escape must work even when the client script or server does not.
- The artifact iframe carries only `data-artifact-src` and is navigated exclusively by `replaceArtifactFrame`, so a chrome whose FIRST begin-load fails has no previous frame to preserve - abandoning the load there leaves an empty frame and an `artifact_revision` that never advances, which is what a session reopened across a server restart looked like. Recoverable outcomes (a transport failure past `ARTIFACT_LOAD_BEGIN_RETRY_DELAYS_MS`, or a `no-handoff` whose one re-handshake also failed) must schedule a fresh attempt through `ARTIFACT_LOAD_RECOVERY_DELAYS_MS` and, once that is exhausted with nothing on screen, surface `setLayoutGateFailure` instead of a silent blank. `superseded` and `out-of-order` must NOT retry: another reviewer or a newer request in this same chrome owns the artifact, and a background retry would fight it. A `superseded` chrome that has nothing on screen still has to say so on the gate overlay (`setLayoutGateFailure` with a takeover reload), because the takeover notice lives under the top bar, which the overlay covers - without that the page holds the checking spinner for the full gate hold and then reveals an empty frame with its only recovery control hidden the whole time. A `superseded` chrome that already shows an artifact must keep it and use the banner alone.
- The layout-warning inbox's rules are the product contract, not implementation detail - `src/layout-warnings.js` and `test/layout-warnings.test.js` are the authority, and the lifecycle is also restated for users in README and for agents in the poll guidance. Two invariants are easy to break by accident:
  - Nothing may clear a warning except a newer artifact revision plus a **complete** pass at the **same viewport class** that no longer detects it. Not a closed drawer, a checked box, a queued or delivered prompt, an agent reply, a reload in flight, a temporarily absent element, another viewport passing, or a failed diagnostic run.
  - Adding a route or UI action that emits `feedback` for a detection makes the whole feature regress to the auto-repair churn it replaced. Only user actions (`/api/:key/prompts`) and the narrow fatal path may emit it.

- The revision registry (`src/artifact-revisions.js`, README's Revision marks bullet) reads an agent-declared `data-lavish-revisions` registry and `data-lavish-revision` marks; the SDK is read-only and never marks up the artifact, so the served bytes stay identical to the file on disk. Three invariants are easy to break by accident:
  - `resetRevisionRegistry()` in `src/chrome-client.js` must run only right before `replaceArtifactFrame` actually navigates the frame, never unconditionally at the top of that function. A preserved load (`superseded`, `out-of-order`, an exhausted retry) never navigates, so clearing the registry there disables every thread's Reveal change on an artifact that is still on screen and whose SDK will never re-report it. There is no top-bar legend; Reveal lives only on thread replies that name a revision.
  - Every artifact-frame navigation goes through `navigateArtifactFrame`: the first assigns `frame.src` (filling the initial empty document adds no history), and every later one calls the frame window's `location.replace`, which a parent may call across the opaque sandbox origin. Reassigning `frame.src` pushed one joint session-history entry per save, until Chrome refused a script's `window.close()` of the review tab. `frame.src` therefore keeps the first load's URL; nothing may read the current load's token from it.
  - The registry's cap (`entries` in both `revisionLimits()` and the chrome's `REVISION_LIMITS`) must derive from the shared `revisionPalette()` length, not a second hardcoded number - a cap that outgrows the palette hands two revisions the same colour, border, and pattern.
  - The chrome re-validates the postMessage payload as untrusted input from a sandboxed frame: an id or selector over its length limit is rejected outright, never truncated, because a truncated id can collide with another revision's and a truncated selector is still valid CSS pointing somewhere else. `__proto__` is a legal revision id, so lookups use a `Map`/`Set`, never a plain object key.

- The shared Reveal change/Layout issues Reveal marker stays inside the excluded `[data-lavish-ui]` shadow host. It tracks the target's live viewport bounds for its whole flash, cancels prior tracking on another Reveal, and uses instant scrolling without a pulse for reduced motion. `test/reveal-element.browser.test.js` pins this against real scrolling.

- The whiteboard has six easy-to-reintroduce failure modes, all covered by tests or explained in comments:
  - Mermaid skeletons must be materialized again after Excalidraw's scene fonts load; the first synchronous materialization uses a narrower browser-serif fallback and stores text bounds that clip the eventual Excalifont glyphs.
    Keep the font-load and second-conversion ordering in `convertExcalidrawSkeletonsAfterFontsLoad`, and keep the versioned saved-scene repair expansion-only so it never overwrites user geometry or content.
    The real-browser regression in `test/whiteboard-render.browser.test.js` covers both paths.
  - Mermaid node labels use `<br>` / `<br/>` and a two-character `\n` as line breaks. `parseMermaidToExcalidraw` copies `vertex.text` onto skeleton `label.text` unchanged, so those markers stay literal characters and Excalidraw concatenates "classify<br>checks" into one line. `restoreMermaidLabelLineBreaks` in `src/whiteboard-core.js` must run on skeletons before `convertToExcalidrawElements` (and again on materialized text with a measure pass) so Excalidraw `text` / `originalText` get real `\n` and the box sizes to the line set. When that pass grows a node-label container (rectangle, ellipse, diamond) from the center, it must also reposition the independently stored bound-text `x`/`y` into the new box; skip labelled arrows, whose labels sit at path midpoints. `convertSource` mounts without `restore()`, so Excalidraw will not re-derive that geometry on first paint. `test/whiteboard-core.test.js` and the clipping browser fixture cover both break forms, the fusion case, bound-text recentering, and labelled-arrow skip.
  - The converter breaks with mermaid >= 11.14.0: its parsers reach into mermaid's rendered DOM/db internals, and newer versions silently degrade class/ER/state diagrams and subgraph flowcharts to image fallbacks. `mermaid` is pinned EXACTLY (independent of the artifact-facing Mermaid CDN version in `src/design-reference.js`), and `test/whiteboard-pins.test.js` fails any unpinning; bumping requires a live re-probe of native conversion.
  - Excalidraw's theme must be passed only through the `<Excalidraw theme>` prop, and persisted `appState` must never carry `theme` or a dark-space `viewBackgroundColor`: dark mode renders through an invert filter, so a dark background value or a second theme application double-inverts into a washed-out canvas (`src/whiteboard-core.js` strips both at the persistence boundary).
  - `/whiteboard-assets/*` must keep `Access-Control-Allow-Origin: *` (the opaque-origin frame's font fetches are CORS-gated), `Cache-Control: no-cache` (an unversioned bundle URL plus memory cache serves stale editors after upgrades), and `dotfiles: "allow"` in sendFile (a checkout under a dot-directory otherwise 403s every asset).
  - A sidecar's presence is not a user edit: `startFromConversion` autosaves on view, including scroll/zoom from fit-to-content. `handleInit` must go through `resolveWhiteboardInitAction` so a Mermaid-source change silently re-converts an unmodified-since-conversion scene and only prompts when `savedSceneHasPreservableEdits` finds preservable edits. Treating "saved scene exists with a different hash" as the prompt condition brings back the phantom re-convert/keep banner on live agent updates.
